Техническое задание: Opportunity Content Aggregator
Проект: биржа проектов между студентами и бизнесом
Компонент: дополнительный независимый модуль контент-агрегации
Версия ТЗ: 1.0, 25.10.2026
Исполнитель: Codex / разработчик
Приоритет: MVP без нарушения работы основной биржи
1. Контекст и цель
Основной продукт — биржа, на которой бизнес размещает задачи, студенты находят подходящие проекты, откликаются и приобретают практический опыт. Модуль не должен превращать платформу в социальную сеть или новостной портал.
Цель модуля — автоматически находить релевантные публичные публикации из разрешённых источников, фильтровать и нормализовать их, передавать на модерацию и выводить на главной странице сайта в разделе «Возможности и события».
Успех модуля: главная страница регулярно показывает свежие, достоверные и полезные публикации, а основное действие пользователя остаётся «Найти проект» / «Разместить задачу».
2. Границы MVP
Входит:
•  Источники RSS/Atom, публичные сайты с разрешённым сбором, ручное добавление через админку.
•  Отдельные коннекторы для официальных API при наличии доступа; Telegram и Apify — через включаемые адаптеры с самостоятельными credentials и проверкой правомерности доступа.
•  Настраиваемое расписание, ручной запуск из админки.
•  Нормализация записей, очистка HTML, дедупликация, категоризация, оценка релевантности, проверка свежести.
•  Модерация: черновик → проверка → публикация / отклонение / архив.
•  Публичный API и компактный блок карточек на главной.
•  Логи, метрики, обработка ошибок, ограничение запросов, тесты и документация.
Не входит в MVP:
•  Перепубликация полных текстов, фотографий или видео без разрешения.
•  Автоматические регистрации на мероприятия и заявки от лица пользователей.
•  Поиск или сбор личных данных, закрытых аккаунтов, приватных сообщений.
•  Обход CAPTCHA, авторизации, платных стен, антибот-защиты или лимитов платформ.
•  Комментарии, лайки, подписки, персональная социальная лента.
•  Автоматическое создание «заказов биржи» из внешних публикаций: внешние материалы не должны подменять настоящие заявки бизнеса на платформе.
3. Контентная стратегия
Категории: hackathons, grants, internships, accelerators, events, education, student_success, startup_news, business_opportunities.
Приоритет первых релизов: хакатоны/соревнования; гранты/акселераторы; стажировки/практика; отраслевые мероприятия; возможности для предпринимательства. География: Казахстан в приоритете, международные возможности — при доступности гражданам Казахстана или при явной пользе целевой аудитории.
Ключевое правило: истории успеха пользователей платформы создаются из проверенных внутренних данных и публикуются отдельно; никакие вымышленные сделки, показатели или отзывы недопустимы.
4. Архитектура и интеграция
Реализовать отдельный модуль, адаптированный под существующий стек проекта. Сначала изучить репозиторий и выявить фреймворк, базу данных, механизм авторизации, очередь задач, UI-компоненты, схему деплоя и тестирования. Не вводить новую инфраструктуру без необходимости.
Рекомендуемые логические компоненты:
1. SourceRegistry — настройки источников и их состояние.
2. ConnectorRegistry — плагинообразные коннекторы с единым интерфейсом fetch(since, cursor, limit) -> FetchResult.
3. Scheduler/Worker — периодический опрос; идемпотентные задачи и защита от параллельного запуска одного источника.
4. Normalizer — единая структура публикации, канонизация ссылок, санитарная обработка текста.
5. Deduplicator — идентификатор источника + хеш нормализованного URL, опционально похожие заголовки.
6. RelevanceEngine — правила и веса; ИИ необязателен.
7. ModerationService — конечный автомат статусов и журнал действий.
8. ContentAPI — публичные и административные endpoints.
9. HomepageWidget — карточки на главной без влияния на ключевые CTA биржи.
Сервис может жить в существующем монолите как изолированный пакет, отдельный микросервис не обязателен. Вся логика сбора должна исполняться на сервере. Публичный сайт не должен обращаться к внешним парсерам напрямую.
5. Источники и политика доступа
5.1 MVP
•  RSS/Atom: использовать стандартные парсеры; обрабатывать ETag / Last-Modified, если они доступны.
•  Официальные сайты: применять доступные API/RSS; HTML-сбор — только если он разрешён правилами ресурса; соблюдать robots.txt как дополнительный сигнал, разумные лимиты и условия использования.
•  Ручные публикации из админки.
5.2 Расширения
•  Telegram: доступные публичные каналы через разрешённый способ интеграции; Bot API не даёт универсального поиска по всем публичным каналам. Альтернативные клиентские API требуют отдельной оценки условий платформы, безопасности и управления сессиями.
•  Apify: адаптер для конкретных разрешённых Actors через API, с квотами и бюджетным ограничением. Не предполагать, что каждый Actor одинаково доступен или разрешён.
•  YouTube: официальные API при наличии ключей и с учётом квот.
•  Threads, Instagram, TikTok, Reddit: не обещать универсального сбора; добавлять только при наличии легального/доступного API или совместимого поставщика данных и проверки ограничений.
Для каждого источника хранить source_type, name, base_url, enabled, category_mapping, fetch_interval, last_success_at, cursor, rate_limit, credential_reference (не сам секрет), rights_notes, failure_count.
6. Структура данных
Минимальная сущность AggregatedPost:
{
  "id": "uuid",
  "source_id": "uuid",
  "external_id": "string|null",
  "source_name": "string",
  "source_url": "https://example.org/post",
  "canonical_url": "https://example.org/post",
  "title": "string",
  "summary": "string",
  "category": "hackathons",
  "tags": ["IT", "Kazakhstan"],
  "language": "ru",
  "country": "KZ|null",
  "event_date": null,
  "deadline": null,
  "published_at": "ISO-8601|null",
  "collected_at": "ISO-8601",
  "relevance_score": 78,
  "status": "pending_review",
  "image_url": null,
  "content_hash": "sha256"
}
Отдельные таблицы/коллекции: ContentSource, AggregatedPost, CrawlRun, ModerationAudit, ModuleSettings. Индексы по status, category, published_at; уникальность (source_id, external_id) при наличии external_id и/или canonical_url/content_hash. Фактическую схему адаптировать к существующей БД.
Поля deadline и event_date не придумывать, при неуверенной экстракции оставлять null; если срок уже прошёл, не показывать как открытую возможность.
7. Алгоритм обработки
1. Worker выбирает включённые источники, которым пора обновиться.
2. Коннектор получает ограниченное количество новых материалов (с таймаутами, пагинацией и курсором).
3. Нормализатор извлекает заголовок, URL, дату и допустимый короткий анонс; удаляет HTML/script, трекинговые параметры URL, лишние пробелы.
4. Дедупликатор отклоняет повторы; если внешний источник исправил пост — безопасно обновляет только разрешённые поля.
5. Фильтрация по тематике, языку, географии, свежести и стоп-словам; весовые правила хранятся в конфигурации.
6. Алгоритм выставляет relevance_score 0–100; конфигурируемый порог, например 60.
7. Подходящие записи переходят в pending_review и не публикуются публично, пока не одобрены.
8. Модератор одобряет, редактирует краткий анонс, отклоняет либо архивирует материал.
9. Публичный API возвращает только published, с учётом срока события и даты публикации.
10. Устаревшие события автоматически архивируются по конфигурируемой политике.
На MVP никаких внешних платных LLM-вызовов по умолчанию. Позже можно добавить интерфейс ContentEnrichmentProvider для классификации/резюмирования с жёсткими лимитами затрат, логированием и отключением. ИИ не должен выдумывать факты или ссылки.
8. Релевантность
Конфигурируемая оценка:
•  совпадение категории (+30);
•  сильное совпадение ключевых слов в заголовке (+25);
•  совпадения в описании (+15);
•  Казахстан или подходящая международная программа (+10);
•  высокая свежесть (+10);
•  проверенный источник (+10).
Штрафы: устаревший материал, реклама без ясной пользы, нерелевантные темы, слишком мало фактов, подозрительные ссылки. Это стартовая эвристика, которую надо покрыть тестами и позволить менять без переписывания кода.
9. API (ориентировочные пути)
Префикс пути и авторизацию согласовать с текущим backend.
Публичные:
•  GET /api/content/posts?category=&limit=&cursor= — опубликованные карточки; предельный limit, сортировка, пагинация.
•  GET /api/content/categories — категории и счётчики (при необходимости).
Административные (только для ролей с правом модерации):
•  GET /api/admin/content/posts?status=&source=&category=;
•  POST /api/admin/content/posts — ручная публикация/черновик;
•  PATCH /api/admin/content/posts/{id} — редактирование полей;
•  POST /api/admin/content/posts/{id}/approve;
•  POST /api/admin/content/posts/{id}/reject;
•  POST /api/admin/content/posts/{id}/archive;
•  GET /api/admin/content/sources / POST / PATCH;
•  POST /api/admin/content/sources/{id}/sync — ручной запуск с ограничением частоты;
•  GET /api/admin/content/runs — журналы и ошибки;
•  GET/PATCH /api/admin/content/settings — расписание, порог оценки, включение модуля.
Стандартная обработка ошибок, RBAC, валидация входных данных, серверное ограничение размера запросов; документировать OpenAPI по принятому в проекте способу.
10. Админ-панель
Раздел «Контент / Агрегатор»:
•  вкладки «На проверке», «Опубликовано», «Отклонено», «Архив»;
•  поиск, фильтры, сортировка, предпросмотр карточки и открытие первоисточника;
•  кнопки «Опубликовать», «Отклонить», «Архивировать», «Редактировать»;
•  управление источниками, настройками и ключевыми словами;
•  история запусков, число найденных/отсеянных/одобренных, ошибки по источникам;
•  ручной запуск и выключатель модуля.
Все административные операции логировать: пользователь, действие, объект, дата, изменения.
11. UI главной страницы
Блок «Возможности и события» под основными CTA биржи. По умолчанию 3–6 карточек с названием, коротким собственным анонсом (не полным скопированным текстом), категорией, датой, названием источника и ссылкой «Подробнее у источника». Показывать время/дедлайн только при подтверждённых данных. Внешние ссылки — безопасное открытие (rel="noopener noreferrer" и разумная политика target).
Адаптивность: мобильная, планшет, десктоп. Использовать существующую дизайн-систему. Скелетон загрузки; если данных нет или модуль отключён — скрыть блок без пустой дыры и ошибки страницы. Ключевые CTA биржи всегда остаются выше блока.
Отдельный внутренний блок «Успешные проекты платформы» — другая сущность/источник данных, не смешивать с агрегированными новостями.
12. Расписание и эксплуатация
•  Стандарт: обновление раз в 6 часов; настраивается до ежедневного или другого разумного интервала.
•  Применить имеющийся механизм фоновых задач или cron; не запускать парсинг при каждом запросе страницы.
•  Timeout, ограничение частоты, повторы с exponential backoff и jitter; предельное число попыток.
•  Idempotency и lock для источника, продолжение обработки других источников при ошибке одного.
•  Учёт квот API, верхние лимиты числа результатов/сутки и платных вызовов, безопасное прекращение при превышении бюджета.
•  Секреты только через переменные окружения / Secret Manager; не хранить в БД открытым текстом, не включать в логи.
•  Метрики last_success, items_fetched, accepted, rejected, duplicate, error_rate, duration, estimated_cost.
•  Модуль отключается флагом конфигурации и не влияет на доступность основных операций биржи.
13. Безопасность, права и качество
•  Сбор только открытых данных при наличии правового и технического доступа; учитывать условия и лицензии источников.
•  Не обходить авторизацию, CAPTCHA, блокировки, лимиты или платные ограничения.
•  Не копировать полные материалы и изображения без права использования; по умолчанию использовать короткий собственный анонс и ссылку на первоисточник.
•  Не собирать личные данные из социальных сетей без необходимости и правового основания.
•  Защита от SSRF: allowlist доменов, блокировка локальных/приватных адресов, контроль редиректов и DNS-rebinding; валидация URL.
•  Защита от XSS/HTML-инъекций: санитарная обработка, безопасный рендер текста.
•  Логи без токенов, cookies и персональных данных.
•  Фиксация источника и времени получения, механизм удаления/отзыва по запросу правообладателя и администратора.
14. Тестирование и критерии приёмки
Unit-тесты
•  парсинг RSS и нормализация дат, URL;
•  корректная дедупликация одного поста из разных запусков;
•  фильтрация по языку, категории, свежести;
•  отклонение невалидных URL, HTML/script;
•  корректные переходы статусов;
•  отсутствие внешнего обращения при enabled=false.
Integration-тесты
•  mock_source -> worker -> database -> moderation -> public API;
•  повторный запуск без дублей;
•  отказ одного источника не останавливает остальные;
•  недоступный API, timeout, 429, 5xx, повреждённые данные;
•  административный endpoint недоступен неавторизованному пользователю;
•  удаление/архивация исключает карточку из публичного API;
•  секреты не появляются в ответах и логах.
E2E/UI
•  на главной показаны 3–6 одобренных карточек в корректном порядке;
•  переход к первоисточнику работает;
•  пустой список не ломает страницу;
•  адаптивность на ширине мобильного экрана;
•  выключение модуля не затрагивает размещение проектов, отклики, авторизацию и поиск.
Критерий завершения MVP: на тестовом RSS-источнике и одном разрешённом сайте или ручном источнике полностью работает сквозной процесс, админка и карточки; автоматический запуск не создаёт дублей, ошибки изолированы, основные функции биржи не регрессируют. Внешние соцсетевые адаптеры допускается оставить отключёнными до получения законного доступа.
15. Этапы реализации
1. Аудит репозитория, карта интеграции, миграции и feature flag.
2. Модели данных, SourceRegistry и RSS-коннектор, ручной ввод.
3. Worker, фильтрация, дедупликация, очередь модерации.
4. Админ-панель, публичный API, UI главной страницы.
5. Логи, безопасность, unit/integration/E2E тесты, документация.
6. После приёмки MVP: отдельные адаптеры Telegram / Apify / YouTube и другие разрешённые источники.
16. Что должен сдать Codex
•  Работающий модуль в текущем репозитории без слома существующей архитектуры.
•  Миграции, конфигурацию и .env.example без реальных ключей.
•  Документацию по добавлению нового источника и команды запуска.
•  Демоданные с явной отметкой demo, которые не публикуются как настоящие события в production.
•  Автоматические тесты и результаты их запуска.
•  Сводку внесённых файлов и изменений.
•  Список ограничений и задач, отложенных после MVP.
17. Инструкция Codex
> Изучи действующий репозиторий биржи студентов и бизнеса и реализуй отдельный модуль **Opportunity Content Aggregator** строго по этому ТЗ. Сначала проведи аудит архитектуры, затем составь короткий план интеграции и выполни его. Не заменяй существующий стек без обоснования. Делай изменения изолированно с feature flag; любые недоступные интеграции оформляй как отключаемые адаптеры, а не как фиктивно работающие источники. Сохрани основное позиционирование продукта — биржа проектов. Создай тесты, миграции и документацию, выполни доступные проверки и честно укажи, что не проверялось. Не добавляй платных сервисов и ключей без явной необходимости.
