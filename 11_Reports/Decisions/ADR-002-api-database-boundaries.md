# ADR-002: Границы API и целостность существующей БД

Статус: реализовано. Дата: 25.10.2026.

## Контекст

Рабочий интерфейс использует `/api/platform` с view/action, но обработка 27 команд и публичных/приватных чтений находилась в одном файле. В профильном route была транзакция с таблицами и отдельная обработка ошибок. Для новых функций нужна понятная граница данных без потери текущего процесса и пользовательских записей.

## Варианты

1. Ввести новый набор REST-маршрутов, сразу переписать все вызовы UI и одновременно сменить схему БД.
2. Сохранить внешний контракт, разделить внутренние команды и чтения, унифицировать HTTP-границу и усилить ограничения существующих таблиц.

## Решение

Выбран второй вариант. Next.js остаётся единым приложением с общей PostgreSQL. HTTP route не содержит профильных SQL/Prisma операций; серверные сервисы используют один клиент БД. Команды разбиты по бизнес-действиям, чтение — на public/account/admin. Нет нового универсального репозитория или интерфейса для каждого класса: Prisma уже даёт транзакционный доступ, нужный данному приложению.

Права проверяются в серверном коде по текущему пользователю, владельцу/участнику и состоянию; на изменениях — внутри транзакции. В публичных и административных списках разрешённые поля перечислены явно. Общая HTTP-обработка ограничивает поток, проверяет JSON/origin, выдаёт стабильный code и no-store. Профиль и биржа сохраняют существующие payload и формат data/error. Better Auth остаётся отдельной областью ответственности.

OpenAPI 3.1 генерируется из действующих Zod request schemas. Разрешения и бизнес-условия описаны рядом в генераторе; тесты проверяют совпадение списка команд и схем. В первоначальном этапе response DTO были общими. Обновление 25.10.2026: выделены точные строгие wire-схемы всех 8 разделов и 27 команд; TypeScript-типы UI выводятся из этих схем, а E2E проверяет реальные ответы. Общее описание оболочки заменено именованными схемами и anyOf для совпадающих результатов.

В Prisma сохранены имена таблиц и столбцов. Транзакционная SQL-миграция добавляет связь чек-листа с версией условий, ограничивает один selected-отклик на проект, проверяет статусы и согласованность заявлений об оплате. Индексы соответствуют существующим фильтрам и сортировкам. Четыре одиночных индекса заменены составными с теми же ведущими столбцами. История и строки не исправляются автоматически.

## Причины и последствия

Изменение HTTP-стиля сейчас не решает дополнительную пользовательскую задачу; сохранение адресов уменьшает площадь регрессии. Разделение кода делает будущий агрегатор самостоятельным модулем, не ещё одной веткой биржи. Новую область контента нужно будет проектировать отдельно, когда начнётся соответствующий этап.

Команды остаются RPC: нельзя считать все POST идемпотентными или автоматически повторять их после неизвестного исхода. GET не изменяет бизнес-состояние. Применение ограничений может блокировать таблицы; для текущего локального объёма используется короткое окно обслуживания. При нарушении старых данных миграция останавливается и откатывается, требуя изучения причины.

## Риски и дальнейшая работа

Проверка PostgreSQL связей не является RLS: локальный owner имеет широкие права, а авторизация строк выполняется приложением. Production должен использовать подготовленную отдельную DML-роль. Ускорение запросов на реальном масштабе ещё не измерялось. При выделении новых внешних потребителей отдельно оценить ресурсные маршруты/версионирование и явные response DTO, сохраняя переходный контракт.
