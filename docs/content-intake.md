# Закрытый сбор возможностей: этап 3

Продолжение от 26.10.2026: [HTML/RSS-сбор и общий поиск возможностей](opportunity-discovery.md). Добавлены HTML-источники, категории грантов/стипендий/обучения и текстовые фильтры; ниже сохранено описание предыдущего этапа.

Продолжение реализовано в этапе 4: [модерация, история и публичная лента](content-moderation.md), [текущая приёмка](qa/content-moderation.md). Описание ниже сохраняет границы первоначального этапа сбора; ограничения публикации заменены соответствующим этапом 4.

Модуль принимает ручные материалы и RSS/Atom в закрытую очередь администратора. Он отделён от заказов маркетплейса: импорт не создаёт `Project`, публичную карточку, рассылку или уведомление пользователю. Новые материалы получают только `pending_review`.

Этот документ описывает реализованное поведение. Итоговая приёмка, полный набор проверок и состояние локального запуска — в [QA-отчёте](qa/content-intake.md). Архитектурные причины зафиксированы в [ADR-004](../11_Reports/Decisions/ADR-004-content-intake.md).

## Управление через интерфейс

Путь: кабинет администратора → вкладка **«Сбор возможностей»**. Здесь доступны флаг модуля, создание источника, включение и отключение источников, постановка RSS-импорта в очередь, ручной ввод и просмотр материалов/запусков.

1. Создать источник с типом `manual` или `rss`, точным разрешённым доменом, описанием основания использования и ограничений. Для RSS обязателен адрес ленты. Ссылка на условия использования необязательна, но полезна для проверки источника.
2. Проверить условия конкретного источника и допустимый сценарий использования. Поле `rightsNote` хранит запись администратора; наличие RSS и заполнение поля не подтверждают права автоматически.
3. Включить источник и модуль. В БД оба флага по умолчанию `false`; форма создания всегда добавляет выключенный источник. API допускает явное `enabled: true` при создании, однако общий флаг модуля продолжает действовать.
4. Для RSS дождаться фонового прохода или нажать «Поставить импорт в очередь». Эта кнопка только создаёт задание; HTTP-запрос к источнику делает отдельный worker. Для ручного источника заполнить ссылку, заголовок, краткое содержание и категорию.
5. Обновить очередь и проверить результат. Интерфейс показывает последнюю редакцию материала, исходную ссылку, оценку релевантности, дату источника и счётчики запусков. Автоматического обновления очереди в браузере нет.

При выключенном модуле чтение и настройка источников продолжают работать, а ручное сохранение и новые запросы импорта отклоняются. Worker проверяет флаги перед внешним запросом и повторно в транзакции сохранения. Уже выполняющийся HTTP-запрос не отменяется переключателем; если при фиксации модуль или источник выключен, результат пропускается без сохранения материалов.

## API

`GET /api/admin/content?page=1` требует активную сессию администратора. Чтение не обращается к RSS и не создаёт задания. Ответ содержит настройки, до 100 источников, 20 материалов выбранной страницы с одной последней редакцией и 30 последних запусков. `total` относится ко всем материалам, `page` — только к материалам; допустимы страницы от 1 до 10000.

`POST /api/admin/content` принимает JSON с полем `action`. Требуются текущая роль `admin`, активный аккаунт, совпадающий с настроенным адресом сайта `Origin` и `Content-Type: application/json`. Вне локального режима требуется подтверждённый email. Сервер повторно читает статус и роль внутри транзакции. Максимум тела — 32768 байт, включая фактически прочитанный поток.

| Действие           | Основные поля                                                    | Поведение                                                                                                                                                                                                               |
| ------------------ | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `setModuleEnabled` | `enabled: boolean`                                               | Меняет общий флаг и пишет аудит; доступно при выключенном модуле.                                                                                                                                                       |
| `createSource`     | `name`, `type`, `allowedHost`, `rightsNote`; для RSS — `feedUrl` | Создаёт источник; дополнительно поддерживает `termsUrl`, `enabled`, `intervalMinutes`, `maxItems`.                                                                                                                      |
| `setSourceEnabled` | `sourceId`, `enabled`                                            | Включает или отключает источник. При переходе из выключенного состояния во включённое обнуляет счётчик ошибок, сохраняя `nextRunAt`.                                                                                    |
| `requestSync`      | `sourceId`                                                       | Для включённого RSS при включённом модуле возвращает существующий активный запуск либо создаёт `queued`. До `nextRunAt` новый запуск отклоняется с HTTP 429.                                                            |
| `addManualContent` | `sourceId`, `url`, `title`                                       | Для включённого ручного источника при включённом модуле сохраняет материал/редакцию либо возвращает дубль. Дополнительные поля: `summary`, `category`, `geography`, `language`, `publishedAt`, `deadline`, `eventDate`. |

Успешный ответ имеет форму `{ "data": ... }`. Изменение флага возвращает `{ "saved": true }`, создание источника — `{ "sourceId": "..." }`, постановка задания — `{ "runId": "...", "status": "queued|running" }`, ручной ввод — `{ "kind": "created|updated|duplicate", "itemId": "..." }`. Все эти ответы используют HTTP 200.

Ошибки возвращаются в общем формате API: `error` и `code`. Типовые статусы: 400 — поля, URL или страница; 401/403 — доступ; 409 — состояние/конкурентное изменение; 413 — размер тела; 415 — тип тела; 429 — ожидание следующего запроса. Подробности контрактов и примеры находятся в [описании API](api.md) и генерируемой OpenAPI-спецификации.

## Данные и дедупликация

| Таблица                 | Назначение                                                                      |
| ----------------------- | ------------------------------------------------------------------------------- |
| `ContentModuleSettings` | Единственная строка `content`, общий флаг сбора.                                |
| `ContentSource`         | Тип, разрешённый домен, условия, расписание и состояние источника.              |
| `ContentItem`           | Идентичность материала внутри источника, каноническая ссылка и закрытый статус. |
| `ContentRevision`       | Последовательные неизменяемые снимки содержания.                                |
| `CrawlRun`              | Очередь, lease, результат, безопасный код ошибки и счётчики одного запуска.     |
| `ContentAudit`          | Неизменяемый журнал административных действий и результатов импорта.            |

Идентичность сопоставляется внутри одного источника по SHA-256 канонического URL или `externalId`. В БД уникальны пары источник–URL и источник–внешний идентификатор. Если два признака указывают на разные материалы, импорт не объединяет их автоматически и завершается ошибкой.

Из URL удаляются фрагмент и известные маркетинговые параметры `utm_*`, `gclid`, `fbclid`; остальные параметры сохраняются. Равенство хеша содержания **последней** редакции означает дубль. Изменение добавляет следующую редакцию: A → B → A → A даёт три редакции, а последний повтор ничего не добавляет. Индекс исторических хешей не уникален. Материалы в `rejected`, `archived` или `withdrawn` повторный импорт не возвращает в очередь.

Редакции и аудит защищены триггерами БД от обновления и удаления. Запись материалов, счётчиков успешного запуска, расписания и аудита выполняется одной транзакцией: сбой фиксации откатывает весь этот результат. Отдельная транзакция отмечает запуск как неуспешный. Данные заказов и существующая история маркетплейса в этом потоке не изменяются.

Новые даты и технические значения сохраняются в UTC. Неизвестная или неоднозначная дата остаётся `null`; исходная строка даты публикации сохраняется отдельно в `publishedAtRaw`. RSS-импорт не выводит дедлайн или дату события из текста. Ручной API принимает явные ISO-даты с часовым поясом, но форма текущего интерфейса эти дополнительные поля не показывает.

## Нормализация и оценка

RSS 2.0 и Atom разбираются без перехода по ссылкам внутри материала и без загрузки полной статьи. Заголовок и краткое содержание переводятся в обычный текст; HTML, `script`/`style` и управляющие символы удаляются. Заголовок ограничен 200 символами, краткое содержание — 600, география — 120, язык — 20, канонический URL — 2000. Для ручного заголовка API требует минимум 8 символов, для нормализованного RSS — минимум 3.

Категория RSS определяется простыми правилами по словам: хакатон, конкурс, стажировка, мероприятие или `other`. Оценка детерминирована: базовые 40 баллов, ещё 35 за известную категорию, 15 за упоминание студентов и 15 за упоминание Казахстана, максимум 100. Оценка помогает разбирать очередь; она не доказывает доступность мероприятия, соответствие аудитории Казахстана или актуальность приёма заявок.

Некорректные отдельные записи отбрасываются и увеличивают `discarded`. Записи сверх лимита одного источника тоже учитываются как отброшенные. `found` — число записей в ленте до этих ограничений. Невалидный/опасный XML или ошибка сохранения делает весь запуск неуспешным.

## Фоновая работа и отказы

Worker обрабатывает один источник за проход. Сначала выбирается старейшее `queued` задание, затем доступный по расписанию включённый RSS без активного запуска. После прохода процесс ждёт 15 секунд; время самого запроса и сохранения добавляется к этому интервалу. Стандартный интервал источника — 360 минут; через API допустим диапазон 60–10080 минут. Это отдельные интервалы: частота проверки очереди не означает обращение к каждому RSS каждые 15 секунд.

Захват выполняется в короткой `Serializable`-транзакции с PostgreSQL advisory lock. Частичный уникальный индекс разрешает максимум один `queued`/`running` запуск на источник. Транзакция и SQL-блокировка не удерживаются во время внешнего HTTPS. Lease запуска — 120 секунд; перед сохранением проверяются его срок и состояние. Просроченный запуск следующий проход переводит в `failed` с `LEASE_EXPIRED`, после чего назначается пауза. Поздний worker не может записать результат в завершённый запуск.

После ошибки растёт `consecutiveErrors` и назначается экспоненциальная пауза от 60 секунд с потолком в один час. Валидный `Retry-After` может продлить её, максимум до 24 часов. Успех сбрасывает ошибки и назначает обычный интервал. После пяти последовательных ошибок выключается только соответствующий источник и создаётся запись `source_suspended`. Администратор проверяет причину и включает его вручную; включение обнуляет счётчик, сохраняя текущий cooldown.

Сетевые ошибки, HTTP 429/5xx и ограничения загрузчика сохраняются как безопасные коды без тела ответа провайдера. Другой источник может обрабатываться в следующих проходах. Если недоступна сама БД, процесс пишет общий код ошибки и повторяет проход; незавершённый запуск восстанавливается через lease после возвращения БД. При выключенном модуле обработка, включая разбор просроченных lease, возобновляется после включения.

## Безопасность внешних запросов

- Загрузчик доступен только серверному коду. URL должен использовать HTTPS на порту 443, без логина, пароля и фрагмента. Домен должен точно совпадать с разрешённым доменом источника; wildcard и переход на другой домен не поддерживаются.
- Перед соединением проверяются все DNS-адреса. Наличие хотя бы одного непубличного IPv4/IPv6 отклоняет запрос. Закрыты loopback, private, link-local, metadata, multicast, зарезервированные диапазоны и обходы через IPv4-mapped IPv6.
- Соединение закрепляется за проверенным адресом. Проверка TLS-сертификата и имени исходного сервера сохраняется. На каждом redirect повторяются проверка URL и DNS; разрешены максимум три перехода внутри того же домена. Переменные окружения proxy не используются.
- Общий таймаут загрузки, включая DNS и переходы, — 10 секунд; тело ограничено 1 MiB. Разрешены XML/RSS/Atom и UTF-8/ASCII. Запрашивается `Accept-Encoding: identity`; сжатые ответы отклоняются, а не распаковываются. HTTP 304 учитывается как успешная проверка без новых материалов.
- XML с DTD/ENTITY отклоняется, размер и вложенность ограничены. Содержимое ленты не исполняется, текст не вставляется как HTML. Ссылки материалов и `termsUrl` загрузчик не обходит.
- В production нет флага, разрешающего приватные сети или отключающего TLS. Тестовый транспорт передаётся только в тестах и не подключается из административного API.

## Запуск и диагностика

Перед запуском применить миграции обычным способом проекта и сгенерировать Prisma Client. Помимо первой миграции `20261026120000_content_intake` нужна последующая `20261026121000_content_revision_occurrences`: она снимает уникальность исторического хеша, сохраняя историю и уникальный номер редакции. Уже применённая первая миграция не переписывается.

```powershell
npm run db:migrate
npx prisma generate
npm run worker:content:once
npm run worker:content
```

`worker:content:once` выполняет один проход; при неуспешном импорте или ошибке процесса возвращает ненулевой код. Отсутствие доступного задания — нормальный результат. Длительный процесс продолжает работать после отдельной ошибки. `SIGINT`/`SIGTERM` останавливают цикл и закрывают соединения БД после текущего прохода.

`npm start` запускает web и content worker под общим supervisor. `npm run dev` запускает только Next.js, поэтому при разработке worker нужно запустить отдельно. На выключенном компьютере фонового сбора нет. Значение `enabled` в интерфейсе само по себе не доказывает, что процесс worker запущен.

При разборе сбоя проверить флаги, `nextRunAt`, `lastCheckedAt`, `lastSuccessAt`, `consecutiveErrors`, статус/lease и `errorCode` последних запусков. В UI видны основные сведения; подробное состояние присутствует в административном GET. Для приостановки использовать флаги, сохраняя историю.

## Проверки и границы доказательств

```powershell
npm test -- tests/content-feed.test.ts tests/content-fetch.test.ts
node scripts/test-db.mjs
npm run test:db
npm run test:content
```

Подготовка БД и проверки выше требуют локального PostgreSQL. `test:content` подставляет только `student_marketplace_e2e` на `localhost`/`127.0.0.1`; интеграционные тесты дополнительно проверяют совпадение `DATABASE_URL` и `DATABASE_TEST_URL`. Не следует направлять их в пользовательскую БД. SQL-проверки ограничений используют транзакции с откатом; интеграционные тесты сервиса сохраняют синтетическую неизменяемую историю, выключают свои источники и восстанавливают исходный флаг модуля. Сброс пользовательских таблиц и переписывание истории для очистки не требуются.

`tests/content-fetch-http.integration.mts` проверяет настоящий локальный HTTPS с проверкой сертификата: успешную XML-загрузку, redirect/DNS, блокирование rebinding, 304 и лимит переходов, 429/5xx без утечки тела, размер/тип/сжатие/таймаут. Шесть тестов этого transport-набора успешно выполнены. Для временного сертификата нужен OpenSSL; поддерживается `OPENSSL_BINARY`, в Windows также используется OpenSSL из установленного Git. Доверенный тестовый CA подключается только в fixture.

Postman CLI в текущем окружении недоступен. Внешний HTTP-провайдер для этих проверок заменён локальной нативной HTTPS-fixture; это не результат выполнения Postman simulation. Тесты сервиса отдельно проверяют права, выключение, повторные запросы, дедупликацию и редакции, конкуренцию, обработку ошибок и восстановление lease. Итоговые числа полного прогона и браузерную приёмку фиксирует отдельный QA-отчёт.

26.10.2026 в 10:18:17 UTC выполнена отдельная read-only проверка [официальной RSS MIT News о конкурсах](https://news.mit.edu/rss/topic/contests) через production `fetchFeed` и `parseFeed`: HTTP 200, `found=50`, `discarded=0`, принято 50 записей. [Metadata-отчёт](../outputs/content-intake/real-feed-check.json) содержит время, счётчики и один пример ссылки/заголовка. БД в этой проверке не использовалась, источник в реестр не добавлялся, материалы не публиковались.

Этот пример подтверждает техническую совместимость конкретной ленты на указанное время. Он не подтверждает спрос в Казахстане, пригодность материалов как действующих возможностей или права на их дальнейшую публикацию. Для любого использования требуется проверять [условия MIT News](https://news.mit.edu/terms-of-use) применительно к выбранному формату. Автоматического вывода о правах модуль не делает.

В 10:33 UTC дополнительно проверен полный путь настоящей ленты через worker в E2E-БД: первый импорт — 50 новых материалов, повтор идентичного ответа — 50 дублей без новых редакций. Источник после проверки выключен, основной модуль не менялся. [Метаданные](../outputs/content-intake/real-import-check.json), включая снятие cooldown только в тестовой fixture. Предыдущая попытка получила `FEED_TIMEOUT` и корректно сохранила отказ без материалов; успешный повтор не удаляет эту историю.

## Ограничения этапа

- Не реализованы редактирование и удаление источника. Доступны создание и переключение активности; отключённая история сохраняется.
- Нет действий редакционной проверки, исправления категории, отклонения/отзыва через интерфейс, одобрения или публичной публикации. Эти сценарии относятся к этапу 4. Закрытые статусы уже ограничены БД для безопасного расширения.
- Нет публичной ленты, рассылок, монетизации, AI-пересказа и загрузки полных статей. Оценка и классификация основаны на простых правилах.
- Нет общей дедупликации разных источников, обхода страниц, HTML-скрейпинга, RSS 1.0/RDF, декомпрессии и иных кодировок. HTTP ETag/Last-Modified не сохраняются и условные заголовки не отправляются, хотя ответ 304 поддерживается.
- Один проход обрабатывает один источник. Действуют лимиты пилота: 100 источников, обычно 50 и максимум 100 записей ленты за проход, одна активная задача на источник. Общий срок хранения и квоты накопленной истории пока не заданы; перед масштабированием нужны политика хранения и оценка объёма.
- Администратор отвечает за проверку условий, аудитории, реального срока подачи и достоверности исходных данных. Автоматическая оценка не заменяет это решение.
