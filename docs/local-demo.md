# Локальная демонстрация без облачного сервера

Решение владельца25.10.2026: реализуем и показываем MVP на компьютере; покупку сервера и внешнее размещение откладываем до финансирования. Oracle/DuckDNS/SMTP не блокируют локальную разработку. Уже подготовленная облачная конфигурация сохраняется для будущего переноса; старые VM и TimScheduleBot не изменяются.

## Запуск на подготовленном компьютере

Дважды открыть `START_DEMO.cmd` в корне проекта либо выполнить:

```powershell
npm run demo
```

Команда проверяет локальную конфигурацию, запускает собственный PostgreSQL на127.0.0.1:55432, применяет миграции, дополняет отсутствующие demo-записи, собирает production-версию и запускает ее на **http://localhost:3000**. Существующие заказы и пароли не сбрасываются. Сборка занимает время: дождаться сообщения Next.js `Ready`. Окно команды остается открытым; остановка веб-сервера — Ctrl+C. Данные БД сохраняются. PostgreSQL можно отдельно остановить `npm run db:stop` после остановки веб-сервера.

При занятом порте команда не завершает чужой процесс и не пересобирает работающий сервер: показывает понятное сообщение. Если это уже наше приложение, его можно использовать; для новой сборки сначала завершить прежний сервер. `.env` должен указывать только на собственную БД `student_marketplace` на127.0.0.1:55432 и loopback URL3000. `LOCAL_DEV_MODE=true`, `DEMO_ENABLED=true`; публичные адреса запрещены.

Первоначально нужны Node.js24 LTS, PostgreSQL18 и установленные зависимости (`npm ci`). Путь к PostgreSQL по умолчанию `C:/Program Files/PostgreSQL/18/bin`; другой путь задается `POSTGRES_BIN`. Новый компьютер нужно подготовить заранее, пока есть интернет. Скрипт запуска не устанавливает программы и не загружает зависимости автоматически. После подготовки локальные страницы, БД, авторизация и процесс заказа работают без облачных сервисов; переходы по внешним ссылкам на работы потребуют интернета.

## Учетные записи и письма

Вымышленные demo-логины/пароль — в `.local/demo-accounts.json`; для показа использовать разные профили или приватные окна браузера для студента, заказчика и модератора. Учетные данные не показывать на проекторе и не добавлять в Git.

Локальные письма сохраняются в `.local/mail`, без настоящей отправки. Для проверки восстановления оператор читает письмо командой `npm run mail` в приватном терминале и открывает локальную одноразовую ссылку. Это разрешенный ТЗ dev-flow; он не доказывает доставку настоящего email. Публичный режим по-прежнему требует SMTP и подтверждения почты.

## Резервная копия и репетиция восстановления

```powershell
npm run db:backup -- --verify
```

Создается новая папка `.local/backups/<timestamp>` с `database.dump`, `manifest.json` и при успехе `verification.json`. Формат PostgreSQL custom, SHA256 файла и отпечатки всех таблиц относятся к **одному экспортированному snapshot**, даже если во время копирования приложение продолжает работать. Пароль PostgreSQL передается через окружение дочернего процесса, а не аргументы команды; настройки чужих libpq service files и PGHOSTADDR не наследуются.

Проверка восстанавливает копию в **новую временную БД** с уникальным именем, сравнивает число строк и SHA256 содержимого каждой таблицы. После успеха удаляется только созданная этой проверкой временная база. При ошибке она остается для диагностики. Основная база не заменяется и не очищается.

Повторная проверка сохраненной копии:

```powershell
npm run db:backup -- --check .local/backups/<timestamp>
```

При несовпадении SHA256 восстановление не начинается. Принимаются только собственные копии внутри `.local/backups`; чужие SQL/dump-файлы нельзя считать безопасными. Проверка подтверждает данные и успешный schema restore, но не заменяет E2E приложения. Скрипт не перезаписывает рабочую БД старой копией; такое восстановление после аварии сначала выполняют в отдельную базу и проверяют результат.

Дамп содержит учетные записи, сессии и приватные данные приложения. Он исключен из Git, не доступен через HTTP и хранится по правилам доступа компьютера. Не публиковать его вместе с исходниками. `.env` и локальные почтовые токены не входят в дамп: защищенную копию конфигурации хранит оператор отдельно. Диск компьютера может выйти из строя — перед показом сохранить проверенную копию на другой защищенный носитель.

## Порядок демонстрации

Полный путь — `demo-script.md`: черновик → модерация → отклик → выбор → два согласия → сдача → конкретные правки → приемка → два закрытия → отдельные заявления об оплате → согласованное портфолио. Все демонстрационные данные обозначены ДЕМО. Показ не считается реальной оплаченной сделкой.

Перед показом: резервирование с проверкой, запуск, вход тремя ролями, проверка каталога и одной рабочей области, репетиция по сценарию. Не запускать E2E и не менять код во время выступления. Тесты используют отдельную БД/порт3100, но production build разделяется каталогом `.next`.

Это локальная демонстрация на одном компьютере. Доступ с телефонов и других компьютеров не включается автоматически: текущий dev-flow намеренно привязан к loopback. После финансирования отдельно готовятся сервер, реальная почта, HTTPS, эксплуатация и условия внешнего пилота.
