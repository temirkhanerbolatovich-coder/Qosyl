# Закрытые файлы проекта

F05, 27.10.2026. Заказчик и назначенный исполнитель передают небольшие файлы внутри рабочей области Qosyl. Файлы хранятся в локальной PostgreSQL, доступны через проверяемый сервером маршрут скачивания и не добавляются автоматически в публичный каталог или портфолио.

## Пользовательский сценарий

После обоюдного подтверждения хотя бы одной версии условий в `/work/{projectId}` появляется раздел «Закрытые файлы проекта». Каждый участник может загрузить PDF, PNG, JPEG или UTF-8 TXT во время выполнения (`in_progress`) и доработки (`changes_requested`). Загрузка сразу открывает файл второму участнику. Она сама по себе не означает формальную сдачу результата.

Исполнитель отмечает собственные загруженные файлы в форме «Передать результат», добавляет комментарий и нажимает «Сдать результат». Сдача принимает от одного до пяти результатов вместе: HTTPS-ссылки и/или файлы. Ссылки могут отсутствовать, если выбран хотя бы один файл. Один файл можно включить в несколько последовательных сдач, но нельзя повторить дважды внутри одной сдачи. Файл заказчика можно скачать как исходный материал, но исполнитель не может выдать его за свой файл результата.

Заказчик читает комментарий и скачивает файлы конкретной сдачи, затем принимает результат или запрашивает исправления по согласованным критериям. Новая сдача сохраняет прежнюю историю. Переход к принятию, завершению или спору не удаляет доступные участникам файлы. Предложение новой версии условий также не стирает материалы ранее согласованной работы; новая загрузка остаётся недоступной до возвращения в выполнение/доработку.

Загрузивший участник может удалить свой файл, пока он не включён ни в одну сдачу. Файл второго участника удалить нельзя. После включения в историю удаление запрещено; строка файла и связи сдач неизменяемы. Неприкреплённый собственный файл разрешено убрать и после завершения работы. Сроки хранения, обращения об удалении и их согласование с сохранностью истории относятся к отдельному этапу F07.

## Форматы и ограничения

| Ограничение                                     | Значение                                                                                 |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Размер одного файла                             | 1 байт — 5 МиБ (5 × 1024 × 1024 байт)                                                    |
| Количество файлов проекта                       | До 20, включая включённые в историю                                                      |
| Сумма размеров файлов проекта                   | До 50 МиБ, для обоих участников вместе                                                   |
| Сумма размеров файлов загрузившего пользователя | До 100 МиБ, по всем проектам                                                             |
| Имя файла                                       | До 120 символов после NFKC/trim; без путей, управляющих и невидимых форматирующих знаков |
| Попытки загрузки                                | До 20 в минуту на аккаунт, проверка до чтения тела                                       |
| Чтение входящего потока                         | Ограничение размера по фактическим байтам и тайм-аут 20 секунд                           |
| Состав сдачи                                    | От 1 до 5 HTTPS-ссылок и файлов вместе                                                   |

PPTX, XLSX, DOCX, архивы, исполняемые файлы, HTML и SVG через эту загрузку не принимаются. Для редактируемых офисных документов остаются существующие HTTPS-ссылки с доступом, предоставляемым заказчику вне Qosyl. Добавление нового формата требует отдельной оценки формата, обработки и рисков.

Расширение и заявленный MIME должны соответствовать разрешённой паре. Проверяются маркеры PDF и EOF, сигнатура/IHDR и предельные размеры PNG, начальные/конечные маркеры JPEG; TXT должен декодироваться как UTF-8 без запрещённых управляющих байтов. Это ограниченные проверки формата: они не являются полным разбором документа, изображений или подтверждением отсутствия вредоносного содержимого.

Для каждой карточки API возвращает `scanStatus: "unscanned"`. Антивируса, CDR, изолированного просмотра и автоматической отправки файлов в сторонний сервис нет. Пользовательский интерфейс явно предупреждает об отсутствии проверки. Участники должны передавать только ожидаемые обезличенные материалы, которыми вправе делиться, и проверять скачанные файлы перед открытием.

Повтор загрузки тех же байтов тем же пользователем в тот же проект возвращает существующий файл по SHA-256, даже если новое имя отличается. Исходные имя и метаданные не меняются. Дедупликация не общая между пользователями и проектами, поэтому ответ не раскрывает наличие чужого файла.

## Доступ и приватность

Сервер повторно читает активность аккаунта, demo-настройку, участников и этап проекта. Для изменений вне локального режима также требуется подтверждённый email. Только текущий заказчик и назначенный исполнитель получают список и скачивание; у администратора нет неявного права читать вложения чужого проекта. До первого двустороннего согласования доступ к файлам закрыт. Блокировка аккаунта прекращает его доступ.

Метаданные отделены от бинарного содержимого: публичные Project/Submission-проекции не включают байты, digest или список вложений. Собственный закрытый API возвращает только id, projectId, uploaderId, filename, mediaType, byteSize, createdAt, submissionIds и scanStatus. URL скачивания каждый раз проверяет доступ, не является публичной или временной подписанной ссылкой.

Скачивание всегда отдаётся как `application/octet-stream` с `Content-Disposition: attachment`, UTF-8 именем, `private, no-store`, `nosniff`, CSP sandbox, same-origin resource policy и no-referrer. Inline-preview не выполняется. Перед отдачей сверяются фактический размер и SHA-256; несоответствие возвращает 503 без повреждённых байтов.

Закрытый путь `/api/attachments/...` запрещён в `submitDeliverable.links` и `setPortfolio.publicLinks`: для сдачи файл выбирается через attachmentIds, а не подставляется как ссылка в обход исторической связи. Нормализуются повторные/обратные слэши и кодирование пути. Этот адрес не становится публичным даже при получении его посторонним; основная защита — серверная авторизация скачивания. Файлы никогда не добавляются в портфолио автоматически.

Приватность действует на уровне приложения, без RLS и сквозного шифрования. Оператор с доступом к PostgreSQL или резервной копии может прочитать содержимое. Пилот не обещает антивирусную защиту, автоматическую очистку, юридически согласованные сроки хранения или отдельный аудит инфраструктуры. Не отправляйте сюда секреты и документы, для которых этих ограничений недостаточно.

## API

Все JSON-ответы используют обычный `{data:...}` envelope и `private, no-store`. Требуется cookie-сессия. POST и DELETE требуют Origin текущего Qosyl.

| Метод и путь                          | Назначение                                                             |
| ------------------------------------- | ---------------------------------------------------------------------- |
| `GET /api/projects/{id}/attachments`  | `{data:{attachments:[metadata]}}`, только участники после согласования |
| `POST /api/projects/{id}/attachments` | Сырые байты одного файла, `{data:{attachment:metadata}}`               |
| `GET /api/attachments/{id}`           | Авторизованное бинарное скачивание, без JSON envelope                  |
| `DELETE /api/attachments/{id}`        | Удаление собственного неприкреплённого файла; `{data:{removed:true}}`  |

POST не использует multipart или base64. `Content-Type` задаёт разрешённый MIME, `X-File-Name` — `encodeURIComponent(filename)`, тело — сам File/Uint8Array. Сервер проверяет доступ и фиксирует попытку rate-limit до чтения потока; проверки повторяются внутри финальной транзакции. Content-Length используется только для раннего отказа, фактический поток всё равно ограничивается.

Пример отдельной команды сдачи через существующий `/api/platform`:

```json
{
  "action": "submitDeliverable",
  "projectId": "own-project-id",
  "links": [],
  "attachmentIds": ["own-uploaded-file-id"],
  "notes": "Критерии проверены; результат находится в выбранном файле."
}
```

Без сессии — 401; недоступный аккаунт/Origin — 403; чужой или отсутствующий файл/проект для файлового API — 404; несогласованные условия, неподходящий этап, квота или уже включённый в сдачу файл при удалении — 409. Неверное имя/тело — 400, превышение размера — 413, неподдерживаемый/несоответствующий формат — 415, частые попытки — 429. Текущие схемы и ответы описаны в [OpenAPI](api/openapi.json).

## Хранение, целостность и эксплуатация

Миграция `20261027030000_project_attachments` добавляет ProjectAttachment с BYTEA и SubmissionAttachment. Составные FK исключают связывание сдачи и файла разных проектов; триггер требует совпадения загрузившего пользователя с автором сдачи. Байты, метаданные и связи истории не редактируются; FK не позволяет удалить файл, включённый в сдачу. CHECK ограничивает MIME, размер, длину имени и формат digest, а также равенство byteSize/octet_length(bytes).

Загрузка/удаление блокируют пользователя (`FOR NO KEY UPDATE`), затем проект (`FOR UPDATE`), защищая пользовательскую и общую квоты от параллельных записей. Создание сдачи берёт блокировку того же проекта и атомарно сохраняет Submission и связи файлов в существующей Serializable-транзакции. Файл не может исчезнуть между проверкой и фиксацией сдачи. Формальные действия модерации, приёмки, оплаты и согласий остаются прежними.

Нового каталога файлов, публичной статики, object storage или отдельной npm-зависимости нет. PostgreSQL backup содержит байты и связи вместе с остальными данными; увеличение БД увеличивает размер/время backup и restore. Копии содержат закрытые материалы и не публикуются. [ADR-013](../11_Reports/Decisions/ADR-013-private-project-attachments.md) описывает выбор хранилища.

Пределы находятся в `src/lib/project-attachments.ts`, не задаются входящим запросом. Новых env-переменных нет; действуют существующие DATABASE_URL, LOCAL_DEV_MODE, DEMO_ENABLED и параметры авторизации. До миграции основной БД требуется проверенный backup/restore; далее `npm run db:migrate`, `npm run build`, обычный локальный запуск. Успешная миграция сама по себе не доказывает восстановимость бинарных данных.

Проверки: `npm test`, `npm run test:attachments`, `npm run test:e2e`, `npm run api:check`, `npm run lint`, `npm run typecheck`, `npm run build`. Attachment runner создаёт новую loopback БД `student_marketplace_e2e_attachments_<случайный суффикс>`, применяет миграции и удаляет только свою успешно проверенную БД; при сбое оставляет её для диагностики. Браузерный runner использует отдельную E2E БД. Фактические результаты и проверка восстановления находятся в [отчёте F05](qa/f05-marketplace-2026-10-27.md).

## Основания решения

Рекомендации OWASP по allowlist, независимой проверке MIME/сигнатуры, ограничениям размера, авторизации и хранению вне webroot использованы как несколько дополняющих барьеров, а не как заявление о полной защите. [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).

API использует серверные Route Handlers и стандартные Request/Response в Next.js 16; динамические параметры маршрутов ожидаются через Promise. Чтение сырых байтов выбрано для явного ограничения одного небольшого файла без multipart/base64 и дополнительной библиотеки. [Next.js 16 Route Handlers](https://nextjs.org/docs/app/api-reference/file-conventions/route).
