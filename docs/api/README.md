# Локальный контракт API Qosyl

Q24: `/api/admin/leads/threads` GET возвращает только локальный статус enabled/configured, POST принимает `{query}` и возвращает до 25 нормализованных кандидатов. Свежая роль admin, Origin, body cap 2048 байт, частотные ограничения и выключатель проверяются сервером. Это read-only preview; Lead/Project не создаются. 429 — локальная квота/пауза провайдера, 503 — отсутствие конфигурации/отказ/недоступность; токен и исходная ошибка провайдера закрыты. [Полный контракт и настройка](../threads-search.md), [QA](../qa/threads-search.md). Схемы запросов и ответов включены в OpenAPI.

26.10.2026: текущий RPC-контракт содержит 30 команд и 10 разделов, включая `backgroundJobs` из Q11. Добавлен отдельный административный маршрут внутреннего сбора материалов. Определения метрик и изменение `views` приведены в [pilot-metrics.md](../pilot-metrics.md). Матрицы и карты схем генерируются по текущим реестрам; исторические отчёты предыдущих этапов сохраняют свои прежние количества.

[openapi.json](openapi.json) описывает существующие `/api/platform`, `/api/profile`, `/api/admin/content` и `/api/health` в формате OpenAPI 3.1. Контракт можно импортировать в инструменты API. Он не содержит ключей, паролей или адреса конкретного развёртывания; сервер задан относительным `/`.

## Источник и обновление

Поля запросов генерируются из тех же Zod-схем, которые использует приложение: `src/lib/validation.ts`, `src/lib/catalog-query.ts`, `src/lib/content-validation.ts` и `src/app/api/profile/schema.ts`. Схемы сериализованных ответов находятся в `src/contracts/api-entities.ts`, `api-responses.ts` и `content-intake.ts`; из них выводятся TypeScript-типы ответов. Генератор — `scripts/generate-api-spec.ts`. Описания прав, состояний и побочных эффектов поддерживаются рядом; добавление команды требует описания её доступа и результата.

Из корня Qosyl:

```powershell
node --import tsx scripts/generate-api-spec.ts
node --import tsx scripts/generate-api-spec.ts --check
npm test -- tests/api-contract.test.ts
```

Команды не обращаются к БД и внешним сервисам. Публикация в Postman workspace и создание новых облачных ресурсов не выполняются.

## Разграничение доступа

- `catalog` и видимая проекция `project` допускают гостя.
- `dashboard`/`portfolio` относятся к текущему пользователю.
- `applications` требует роль заказчика и владение проектом.
- `work` требует участия в проекте; сама роль администратора этого права не даёт.
- `admin`/`pilotMetrics` требуют административную роль. Точный адрес и контакт проекта исключены из административной очереди.
- `backgroundJobs` и отдельный `/api/admin/content` доступны только администратору; GET не запускает фоновые задания или сетевой сбор.
- Команды проверяют актуальные роли, владельца/участника и состояние внутри транзакции. Переданные пользователем ID и имя действия не дают дополнительных прав.
- Изменения требуют cookie-сессию, точное совпадение `Origin` и JSON. Для локального HTTP используется `better-auth.session_token`, для HTTPS — `__Secure-better-auth.session_token`; секреты cookie не вписываются в контракт.

Полная матрица сохранена в `x-view-access` и `x-action-access`. Совместимые селекторы `view` и `action` остаются частью действующего интерфейса; номера версии маршрутам сейчас не добавляются.

## Формат и ограничения

Успех прикладного API: `{ "data": ... }`. Ошибка: `{ "error": "текст", "code": "FORBIDDEN" }`, с необязательным `fields` для ошибок профиля. Ответы содержат `Cache-Control: private, no-store`. Health имеет отдельный небольшой формат `{ "status": "ok" }`/200 или `{ "status": "unavailable" }`/503 и `no-store`.

Лимит тела `/api/platform` — 65 536 байт, `/api/profile` — 16 384 байта, `/api/admin/content` — 32 768 байт; ограничивается поток, а не только заголовок Content-Length. Для каталога страница целая с 1, размер страницы 30, верхняя граница номера 10 000. Пустые фильтры пропускаются; перечисления, диапазоны, календарные даты и соотношение бюджетов проверяет сервер. `dueBefore=YYYY-MM-DD` означает конец дня в UTC+05.

Refinement-проверки Zod не полностью выражаются JSON Schema: будущий срок задания, город для очной работы, HTTPS без встроенных реквизитов, согласованность связанных полей и прав доступа остаются серверными правилами. Генератор преобразует дату задания в строку `date-time`; пример с датой 2099 — синтетический запрос для документации, а не реальное предложение.

В OpenAPI есть отдельные `ViewData_<view>`/`ViewResponse_<view>` для всех 10 разделов и `CommandData_<action>`/`CommandResponse_<action>` для всех 30 RPC-команд. `x-view-response` и `x-action-response` указывают точную схему по селектору. Для общих GET/POST используется `anyOf`: некоторые результаты совпадают, например dashboard и portfolio, либо `{ok:true}` у нескольких команд. Новое поле-дискриминатор в реальный ответ не добавляется.

Все объекты ответа строгие: лишние поля отклоняются при проверке, а не молча удаляются. Обязательные поля, ISO-строки дат, nullable-связи, статусы и вложенные коллекции описаны явно. `view=project` имеет отдельные публичную и собственную проекции. Их общий union описывает варианты формы, но не разрешения: для гостевого ответа сквозной тест дополнительно применяет только публичную схему. Приватные поля в work до согласования остаются пустыми строками по существующему контракту.

`useData('catalog')` и другие вызовы интерфейса получают тип результата из реестра схем; `useAction().run(action, ...)` возвращает результат именно выбранной команды. Общие карточки используют отдельный тип полей отображения. В production ответы не подвергаются дополнительной Zod-перезаписи: контракт проверяется на реальных HTTP-ответах в E2E. `/api/auth/*` обслуживает Better Auth; актуальные операции перечислены в [основном руководстве API](../api.md), формат провайдера здесь не переопределяется.

Проверки: `npm test`, `npm run typecheck`, `npm run api:check`, затем `npm run build` и `npm run test:e2e`. Тесты контракта проверяют синхронизацию OpenAPI, сохранение всех RPC-селекторов, разрешимость ссылок, примеры запросов/ответов и границы внутреннего сбора. HTTP/E2E-проверки отдельно подтверждают реальные ответы приложения; успешная генерация схем сама по себе не доказывает работоспособность БД или фонового процесса.

## Внутренний сбор материалов

`GET /api/admin/content?page=1` возвращает `{data:{settings,sources,items,runs,page,total}}`. Номер страницы — целое число 1–10 000; пагинация относится только к материалам, по 20 на страницу. Каждый материал содержит последнюю ревизию, `total` — количество всех материалов. Дополнительно возвращаются до 100 источников и 30 последних запусков. Чтение доступно администратору и при выключенном сборе.

`POST /api/admin/content` принимает union `ContentCommand` с обязательным `action`. Семь действий описаны отдельно, с картами прав и результата `x-action-access`/`x-action-response`:

- `setModuleEnabled` — включает или выключает внутренний сбор; исходное значение `false`.
- `createSource` — добавляет ручной или RSS-источник, по умолчанию выключенный, с обязательным описанием условий использования. RSS требует `feedUrl`, ручной источник не принимает непустой `feedUrl`.
- `setSourceEnabled` — меняет активность существующего источника.
- `requestSync` — требует включённого модуля и RSS-источника. Возвращает уже активный запуск или ставит новый в очередь; HTTP-ответ не означает завершение загрузки. До `nextRunAt` новый запрос отклоняется с 429.
- `addManualContent` — требует включённого модуля и ручного источника; сохраняет текст в закрытую очередь `pending_review`. Повтор текущей ревизии возвращает `duplicate`, изменение создаёт ревизию. Возврат к более раннему содержимому также создаёт новую ревизию.
- `editContent` — сохраняет новую редакторскую версию и возвращает материал на проверку. Требует itemId, expectedRevisionId, expectedUpdatedAt и reason; закрытую запись сначала возвращают через reopen. Существующая редактура и прежнее одобрение остаются в истории.
- `reviewContent` — принимает publish/reject/archive/withdraw/reopen с теми же идентификаторами и причиной. Publish требует включённых флагов, текущего pending_review снимка с URL и явного будущего expiresAt до 90 дней; более ранний deadline/eventDate ограничивает срок. Прочие решения доступны при выключенном модуле. Устаревшее решение даёт 409.

Настройку модуля и источников можно менять при выключенном сборе. Все изменения повторно проверяют текущую активность аккаунта и роль администратора в транзакции; вне локального режима требуется подтверждённый email. Нужны cookie-сессия, правильный `Origin` и JSON. Входные URL должны быть HTTPS на стандартном порту, без реквизитов и фрагмента; домен ленты или материала должен точно совпадать с разрешённым доменом источника. Связанные условия и проверки безопасности URL выполняются сервером и не полностью выражаются JSON Schema.

Даты ручного материала — явные ISO-строки с часовым поясом или `null`; отсутствующий срок не угадывается. Ограничение будущего срока задания из `/api/platform` к материалам не относится; собственный срок актуальности задаётся только при публикации. Примеры с `example.org` — синтетические данные, добавление источника не выполняет сетевой запрос. Типовые ошибки: 400 — поля, URL или срок публикации, 403 — права/Origin, 409 — состояние/версия, 429 — ожидание запроса; ответы используют общий `ApiError`.

`GET /api/admin/content` поддерживает необязательный status; total считает только выбранный раздел. `GET /api/admin/content/{id}?page=1` доступен admin: item с последней версией, source, history по 20, historyTotal и последние 50 audits. Эти данные не попадают в публичный ответ.

`GET /api/content/posts?limit=6` доступен гостю, limit — целое 1–6. Возвращает только одобренную immutable-редакцию опубликованного актуального материала включённого источника при включённом модуле; иначе `{data:{posts:[]}}`. Стабильный порядок approvedAt/id по убыванию. Поля: id, title, summary, category, geography, language, url, sourceName, publishedAt, approvedAt, expiresAt, deadline, eventDate. Нет внутренних заметок, hash, акторов, источниковых ID и истории. Cache-Control private/no-store; запрос не вызывает сбор. [Поток и ограничения](../content-moderation.md).

После сетевой ошибки статусной команды сначала перечитайте состояние. Автоматического повтора и общего idempotency key у данного интерфейса нет. Платёжные команды сохраняют заявления сторон и не перечисляют деньги.

## Приватные лиды и передача владельцу

`GET /api/admin/leads?page=1&kind=business_request&status=new`: admin-only, страница 1–10000, до 20 записей, total по фильтрам, до 100 operator/client вариантов id+name без email. `GET /api/admin/leads/{id}?page=1`: текущая запись и история по 20 событий с общим total. Это приватные сведения; у клиента нет доступа к этому endpoint.

`POST /api/admin/leads` имеет общий discriminator action и десять вариантов из действующего leadCommandSchema: createLead/editLead/assignLead/verifyLead/recordContact/recordConsent/revokeConsent/closeLead/reopenLead/addLeadNote. Вход JSON до 32768 байт, точный Origin, активный admin, вне local — email verified. Кроме createLead требуется leadId/expectedVersion; запись и неизменяемое событие атомарны. Каждое успешное изменение увеличивает version. Ответ `{data:{leadId,version}}`. Duplicate create по kind+canonical URL возвращает существующую запись, включая закрытую, без изменения состояния. Предел — 60 успешных изменений в минуту на admin.

Исходный URL безопасный HTTPS, не загружается программой; срок создания/редактирования будущий, максимум 90 дней. Переходы стадий и роли/активность адресата проверяются сервером и не полностью выражаются JSON Schema. Запись контакта/согласия — утверждение человека, не отправленное сообщение. Discussion не конвертируется в проект. Примеры с 26.10.2026 датированы и синтетические.

`GET /api/leads?page=1`: только client, до 20 собственных consented актуальных передач и converted ссылок, page/total. Проекция: id,version,status,title,summary,sourceName,sourceUrl,expiresAt,projectId. Нет consentEvidence/conversionHash/ответственного/автора/внутренних событий и чужих данных. Все ответы private/no-store.

`POST /api/leads`: текущий client, Origin и JSON до 65536 байт, leadId/expectedVersion/confirmation=true и полный project по прежнему projectFields. Заказчик должен совпадать с записанным clientId, согласие и срок — действовать. Ответ `{data:{projectId}}`, создаётся один обычный draft через прежний transaction-level handler и обычную модерацию. Действительный идентичный replay возвращает тот же ID, изменённое ТЗ — 409; конкурентный запрос может получить 409, но не второй проект. Предел — 30 успешных операций в минуту. Администратор не получает права создать чужой заказ.

Ошибки используют общий ApiError: 400 поля/адресат, 401 сессия, 403 роль/активность/Origin, 404 чужая/отсутствующая передача, 409 версия/состояние/срок/изменённый replay, 413 размер, 415 media type, 429 частота. [Подробный workflow и ограничения](../private-leads.md), [приёмка](../qa/private-leads.md). Прежние 30 RPC-команд и 10 видов чтения не расширялись этими приватными действиями.

Общий поиск возможностей: GET /api/content/posts и GET /api/admin/content принимают q, category, geography, specialty и page. Публичный limit остаётся 1–6; административная страница — 20 материалов. HTML-источники и новые категории описаны в [инструкции](../opportunity-discovery.md); точные схемы и пределы — в openapi.json. Ответы сохраняют прежние envelopes и редакционные границы.
