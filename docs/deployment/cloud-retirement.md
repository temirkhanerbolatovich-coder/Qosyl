# Удаление старых облачных проектов и сохранение бота

Основание25.10.2026: владелец сообщил, что старые проекты можно убрать, затем отдельно указал, что TimScheduleBot нужен, разрешил его перенос и требует рабочее состояние.

**Последнее уточнение владельца:** освобождать ресурсы только при необходимости; если ресурсов достаточно, ничего не удалять. Ранее показанное удаление SAQ отменено кнопкой Cancel. Никакие VM, диски или VCN не удалены. Лимит2VCN можно обойти выбором существующей VCN и отдельной подсети; это не доказательство нехватки RAM.

- В Oracle Tokyo видны `saq-qurylys-prod` (Stopped) и `assetguard-prod` (Running), обеE2.1.Micro. Это свежая проверка Console; исторические документы не использовались как текущий статус.
- SHA256 локального `Documents/SAQ_QURYLYS_Backup_2026-10-23/SAQ_QURYLYS_2026-10-23.tar.gz` совпадает с сохраненной контрольной суммой. Ранее записанный offline restore40таблиц/243файлов — историческое свидетельство, сегодня восстановление повторно не запускалось.
- Через существующий SSH со строгой проверкой host key подтвержден `timschedulebot.service`: active/running, Python3, `/opt/timschedulebot`, данные `/var/lib/timschedulebot/plans.sqlite3`, конфигурация `/etc/timschedulebot.env`. Значения токена не читались в вывод.
- Для AssetGuard найдены47encrypted backups и5относящихся к нему Docker volumes. Код, данные, конфигурация и bot snapshot собраны в приватный архив источника. SQLite snapshot создан через online backup API, `quick_check=ok`,7таблиц. Бот во время подготовки остался active.

Архивы и transfer receipts находятся только в игнорируемом `.local/cloud-transfer` и приватном прежнем каталоге SAQ; они содержат секреты и не публикуются в Git/новом сайте. Перед удалением облака отдельно проверяются завершение скачивания и SHA256 локального файла. Копия не означает уже проверенное восстановление AssetGuard на другой архитектуре.

## Текущий порядок действий

1. Завершить и проверить локальные копии.
2. Проверить запуск новой Always Free VM в существующей VCN с отдельной подсетью, не изменяя старые VM и их правила.
3. При достаточной квоте оставить старые VM/диски/сети и работающий бот на месте. Перенос бота тогда не требуется.
4. Только если будет доказана необходимость освобождения ресурсов, отдельно определить минимальный объем изменений. Для необратимого удаления снова нужно точное подтверждение; старое неоднозначное сообщение за разрешение не принимать.
5. Если перенос бота действительно понадобится: сначала подготовить новое окружение без запуска polling, при переключении снять финальный snapshot, проверить новый экземпляр и возможность rollback. До этого старый бот остается работать. Два polling-процесса одновременно не запускать.

## Открытые действия

Удаление отменено. После подтверждения владельца попытка создания новой A1 VM завершилась ошибкой Oracle `Out of capacity` в Tokyo AD-1; VM не создана, ее публичный IP отсутствует. Регистрация DuckDNS и перенос бота не выполнялись. Нехватка хостов A1 не является основанием удалять старые AMD VM. Текущий код и архивы — подготовка; существующие сервисы продолжают работу.
