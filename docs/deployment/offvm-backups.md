# Защищённая копия БД Qosyl на Windows-компьютере

[scripts/backup-offvm.ps1](../../scripts/backup-offvm.ps1) создаёт свежий dump установленной серверной службой, скачивает его по SSH и сохраняет вне Oracle VM в зашифрованном виде. Скрипт предназначен для PowerShell 7 на Windows, существующего SSH-ключа с доступом к Qosyl и установленного PostgreSQL 18 `pg_restore`. Новые зависимости, облачные хранилища и системное расписание не настраиваются.

Это дополнительная копия на другом физическом компьютере. Она не заменяет переносимое внешнее резервирование и проверку восстановления после потери Windows-профиля.

## Запуск

Из корня `Qosyl/` сначала проверить DPAPI и ACL без обращения к серверу:

```powershell
./scripts/backup-offvm.ps1 -SelfTest
```

Затем создать реальную копию:

```powershell
./scripts/backup-offvm.ps1
```

При другом расположении инструментов пути задаются явно:

```powershell
./scripts/backup-offvm.ps1 -SshKey 'C:/private/qosyl-key' -PgRestore 'C:/Program Files/PostgreSQL/18/bin/pg_restore.exe'
```

Адрес и имя пользователя SSH, служба `qosyl-backup.service` и каталог `/var/backups/qosyl` в скрипте относятся к текущему размещению проекта. При переносе сервера их нужно проверить и изменить в исходнике. `StrictHostKeyChecking=yes` и BatchMode запрещают незаметное принятие нового host key и интерактивные запросы. Проверенные ключи SSH и парольные фразы не включаются в backup и не печатаются.

## Что проверяется

Каждый запуск создаёт новый каталог `.local/offvm-backups/<UTC-время>-<случайный суффикс>/`. Перед появлением dump его NTFS ACL закрывается от наследования: FullControl разрешён только текущему Windows-пользователю и SYSTEM. Junction/symlink в пути не допускаются, существующий каталог запуска не переиспользуется. Каталог `.local/` исключён из Git и Docker build context.

На сервере штатная служба создаёт backup; проверяются успешный exit, свежий mtime, точная допустимая форма имени, размер и SHA256. Затем SSH передаёт бинарный поток с ограничением 256 МиБ и времени ожидания. PowerShell-текстовое перенаправление для dump не используется.

На Windows совпадение SHA256 и `pg_restore --list` подтверждают целостность скачанного архива. DPAPI `CurrentUser` шифрует его; сохранённый `.dump.dpapi` читается обратно, расшифровывается и повторно проверяется SHA256 и `pg_restore --list`. После успешных проверок удаляются только точные временные plaintext-файлы внутри нового каталога. Удаление файла не является гарантированным стиранием блоков SSD, pagefile или данных памяти.

В `verification.json` записываются дата, размер, hashes, имя архива и результаты; пользовательские строки, cookies, секреты и соединения с БД в него не включаются. На сервере выполняется создание копии, а не restore/seed/migration. Настройка расписания или отправка внешних сообщений не выполняются.

## Восстановление и ограничения DPAPI

Microsoft указывает, что `DataProtectionScope.CurrentUser` привязывает расшифровку к текущему пользователю. Для восстановления необходимо сохранить доступ к соответствующему Windows-профилю и его DPAPI-ключам. Простого копирования `.dpapi` на другой компьютер/в другую учётную запись недостаточно. Скрипт не создаёт независимый переносимый ключ восстановления; пароль SSH и приватный ключ не заменяют DPAPI-ключи.

Для контролируемого восстановления сначала выбрать нужный каталог и сверить SHA256 зашифрованного файла с `verification.json`. Работать под тем же Windows-пользователем в отдельном каталоге с такой же закрытой ACL. Расшифровать файл через `ProtectedData.Unprotect(..., $null, CurrentUser)`, сверить SHA256 plaintext с `plaintextSha256`, затем выполнить `pg_restore --list`. Не выводить байты или содержимое архива в консоль и не сохранять plaintext в общий каталог.

Полный `pg_restore` сначала выполняется только в новой временной БД с явно проверенным именем и доступом. После сравнения схемы и критичных записей оператор отдельно принимает решение о восстановлении сервиса. Старый dump нельзя автоматически восстановить поверх более новых пользовательских данных. Контрольная сумма и TOC-проверка не заменяют полный restore: в этом этапе проверялись скачивание и шифрование, а серверная репетиция полного восстановления описана отдельно в [подготовке выпуска](../qa/release-preparation-2026-11-04.md).

Если скрипт завершается ошибкой, он оставляет `failure.json` с этапом и типом ошибки в закрытом каталоге. Непроверенный plaintext может остаться там для диагностики. Нельзя автоматически удалять весь `.local/offvm-backups`: нужно проверить именно этот запуск, завершить проверку и удалить только известные временные файлы через `Remove-Item -LiteralPath`. При ошибке DPAPI не считать копию пригодной для восстановления.

## Проверка 04.11.2026

Синтетический self-test успешно проверил DPAPI round-trip и ACL. При первой реальной диагностике `pg_restore --list` с stdin завершил чтение после TOC, что вызвало broken pipe при передаче остальных байтов; проверка исправлена на временный файл с закрытой ACL. Начальная копия затем прошла decrypt/hash/TOC, известные plaintext-файлы удалены. Итоговая версия отдельно проверена реальным архивом от 04.11.2026 21:37 по Asia/Qyzylorda: 410680 байт, download/decrypt SHA256 и обе TOC-проверки успешны, plaintext-файлов не осталось. Изменённый синтетический шифротекст отклонён DPAPI. Точные результаты и hashes находятся в `verification.json` нового каталога и `.local/release-2026-11-04/offvm-backup-proof.json`; это не обещание будущих запусков.

Регулярное выполнение пока не настроено. Для будущего задания планировщика потребуются тот же Windows-пользователь, загруженный профиль/DPAPI-контекст, проверенный SSH-доступ и независимая проверка ошибок/давности копии. Само наличие скрипта не означает, что такие запуски уже происходят.
