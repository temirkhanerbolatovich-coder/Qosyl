# Oracle Cloud + DuckDNS: подготовка закрытого пилота

**Облако отложено решением владельца25.10.2026 до финансирования.** Текущая цель — локальная демонстрация по `../local-demo.md`. Ниже сохранены подготовленная конфигурация и история попыток; это не текущая задача на покупку/создание сервера.

Выбор владельца25.10.2026: новая отдельная VM в Oracle Cloud, существующий аккаунт DuckDNS; имя подбирает исполнитель. Рабочий кандидат — `student-project-kz.duckdns.org`. Это не утверждение, что адрес зарегистрирован или сайт уже размещен.

## Состояние

Это нехватка доступных хостов Oracle, а не диска/RAM старых VM. Удаление старых ресурсов не требуется и не выполняется.
- DNS-запись и TLS-сертификат еще не созданы. Для почты владелец выбрал Oracle Email Delivery после появления VM; реальная конфигурация и доставка пока не проверены.
- Один ограниченный повтор с той же конфигурацией также вернул `Out of capacity`; fault domain уже установлен в `Let Oracle choose the best fault domain`. - Локальный Docker daemon недоступен. Compose проверяется через `config --quiet`; сборка контейнера и реальный Linux-запуск пока не подтверждены.

## Состав конфигурации

`Dockerfile` собирает Next.js с не секретными build-placeholder значениями; реальные `.env` и данные не входят в образ. На старте снова проверяются runtime-секреты, HTTPS, SMTP и отключение demo. Приложение работает от непривилегированного пользователя node.

`deploy/oracle/compose.yml`: PostgreSQL18, отдельный процесс миграции, приложение, Caddy и опциональный updater DuckDNS. У PostgreSQL и приложения нет опубликованных host-портов. Отдельная внутренняя сеть используется для БД, наружу выходят только80/443 proxy. Caddy дополнительно защищает весь начальный пилот Basic Auth; приложение продолжает проверять собственные роли и сессии.

В `init-app-role.sh` создается отдельная роль `marketplace_app`: без SUPERUSER, владения схемой, CREATE и TRUNCATE; миграции выполняются ролью владельца. После миграций доступ приложения к `_prisma_migrations` отзывается. Триггеры истории принадлежат владельцу схемы; приложение не может отключить их. Это конфигурация для новой пустой PostgreSQL-volume, а не миграция прав чужой существующей БД. Реальная проверка этих прав на Linux еще требуется.

`/api/health`:200 `{status:"ok"}` после запроса к БД,503 `{status:"unavailable"}` при ошибке, без реквизитов и stack trace. Запросы пула ограничены5секундами. Healthcheck выполняется внутри Docker-сети; снаружи действует пилотный вход.

## Безопасная конфигурация

Для упаковки текущих исходников на Windows: `powershell -NoProfile -File scripts/package-pilot.ps1`. Скрипт собирает явно указанные исходные каталоги и конфигурацию в новый каталог `.local/pilot-package/<timestamp>`, проверяет список архива и записывает SHA256. Реальные env-файлы, `.local`, Git, зависимости, исследования и архивы старых проектов не включаются; включены только два env-шаблона. Это пакет исходников, не резервная копия production-БД и не готовый Linux-образ. Перед передачей сверить `archive-entries.txt`, на сервере сверить SHA256.

1. На новой VM выбрать отдельный каталог, например `/opt/student-marketplace`, и доставить туда исходники без `.env`, `.local`, `research`, `node_modules` и чужих архивов. Архивы старых проектов содержат секреты и НЕ являются частью нового приложения.
2. Скопировать `deploy/oracle/.env.production.example` в `.env.production` того же каталога. Права600, владелец — оператор. Пример содержит пустые обязательные поля и намеренно не готов к запуску.
3. `OWNER_DB_PASSWORD` и `APP_DB_PASSWORD` — разные случайные hex-строки, минимум32байта каждая. `BETTER_AUTH_SECRET` — отдельный случайный секрет. Не передавать секреты в аргументах SSH/Docker-команд и не печатать env.
4. Заполнить реальные SMTP HOST/PORT/USER/PASSWORD/FROM. Допускаются465/TLS и587/STARTTLS с проверкой сертификата. Адрес сайта DuckDNS не создает почтовый ящик и не подтверждает право отправки email.
5. Для отдельного пароля пилота получить bcrypt-хеш командой `docker run --rm -it caddy:2-alpine caddy hash-password`: пароль вводится интерактивно. В env-файле хеш заключить в одинарные кавычки для сохранения `$`. Сам пароль передать только согласованным участникам приватным способом.
6. Первую DNS-запись можно настроить через dashboard DuckDNS: для основного запуска токен не нужен. Если оператор включает профиль `dynamic-dns`, `DUCKDNS_TOKEN` хранится только в защищенном env-файле. `DUCKDNS_IPV4` — фактический публичный IPv4 выбранной новой VM; нельзя ставить адрес старого сервера, домашнего компьютера или пример из теста. Регистрация поддомена — отдельное действие владельца аккаунта.

## Запуск после выполнения условий

Из корня доставленного проекта на новой VM:

```sh
docker compose --env-file deploy/oracle/.env.production -f deploy/oracle/compose.yml config --quiet
docker compose --env-file deploy/oracle/.env.production -f deploy/oracle/compose.yml up -d --build
docker compose --env-file deploy/oracle/.env.production -f deploy/oracle/compose.yml ps
```

Сначала должны успешно завершиться миграции, затем health приложения; после этого запускается proxy. В OCI Security List/NSG и firewall VM открыть80/443, SSH ограничить оператором. Не открывать3000/5432. Не менять сетевые правила других VM. Caddy выпускает сертификат только после корректного DNS и внешней доступности80/443; факт наличия Caddyfile не означает полученный сертификат.

Перед регистрацией участников проверить SMTP TLS/login командой `npm run mail:check -- --connect` в соответствующей серверной конфигурации, затем реальное verification-письмо, вход только после подтверждения и reset. Команда verify не отправляет письмо и сама не подтверждает доставку. Приватный пароль пилота не заменяет подтверждение email.

Демо seed в production запрещен. Первый администратор: обычная регистрация с подтверждением email и серверная команда `npm run admin -- <email>` в контейнере. Создание админа через публичную форму невозможно.

## DuckDNS updater

Сервис выключен по умолчанию. После регистрации поддомена и заполнения трех переменных `DUCKDNS_*` его можно включить отдельно:

```sh
docker compose --env-file deploy/oracle/.env.production -f deploy/oracle/compose.yml --profile dynamic-dns up -d dns
```

Официальный endpoint фиксирован в коде; произвольные URL, несколько доменов и локальные IP отвергаются. По умолчанию CLI только проверяет конфигурацию; `--apply` выполняет HTTPS-запрос, `--loop` повторяет каждые5минут. Успех — только HTTP200 с телом `OK`; `KO`, редирект, timeout и ошибка не считаются успехом. URL с токеном и исключение fetch не печатаются. При смене публичного IP VM нужно обновить `DUCKDNS_IPV4`; updater не угадывает адрес другого компьютера.

Unit-тесты проверяют построение запроса и разбор ответа **без сети**. Реальный update не выполнялся, пока не подтвержден новый IP и владение выбранным поддоменом.

## Что еще требуется

Настоящий SMTP, получение TLS, Linux image build/run, проверка least-privilege роли, резервное копирование и восстановление новой PostgreSQL, внешний smoke с телефона, оператор поддержки и юридические тексты. До этого закрытый пилот не объявляется production-ready. Не использовать `docker compose down -v`, prune или очистку чужих томов.
