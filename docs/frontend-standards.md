# Стандарты frontend Qosyl

Версия 26.10.2026. Применять в пределах разрешённой задачи. Спецификация дизайна сама по себе не разрешает менять работающие сценарии.

После явного запроса на внедрение действует дизайн-система 1.0: source tokens — src/lib/design-tokens.json, локальные Inter/Manrope, Light/Dark/System и исходный логотип пользователя. Ранее подготовленные документы инфраструктурного этапа являются историческими. `npm run ui:tokens` регенерирует CSS и проверяет контраст; новый HEX добавляется в JSON, а не в компонент.

## Структура и данные

Сохранять Next App Router, server-only границы и strict TypeScript. Не расширять use client на layout или тяжёлую ветку из-за одного интерактивного control. Сверять данные с существующими contracts/валидацией. Не добавлять запросы или мутации при раскрытии инструментов, если это меняет существующий смысл действия. Независимые чтения можно выполнять параллельно; кеш авторизованных данных нельзя делать общим между пользователями.

Общий компонент выделяется из повторяющихся семантики/поведения, а не ради единообразного имени. Сначала использовать platform.tsx, SiteHeader, OpportunityFilters и существующие формовые patterns. `globals.css` сейчас сочетает Tailwind import и обычные классы — не создавать второй конкурирующий theme provider. Предлагаемые токены вводятся отдельной последующей задачей с проверкой отображения.

## Layout и контент

У страницы один main от корневого layout и осмысленная иерархия заголовков. Grid для структуры; Flex для локального выравнивания. Не фиксировать высоту содержательного текста. У контейнеров с длинным названием — min-width:0, осмысленный перенос, никаких общих overflow:hidden, скрывающих дефект. Таблице допустима собственная обозначенная горизонтальная прокрутка; всей странице — нет.

Сохранять query-параметры, выбранные ID, ввод форм и глубокие ссылки. Недопустимо решать ширину удалением полей бюджета, срока, обязательных предупреждений, ДЕМО и условий оплаты. Форматировать ₸ и даты через существующие helpers; неизвестную дату не угадывать. Проверять RU/KZ, длинные названия, переносы и пустые данные.

## Controls и состояния

Для действия — button с правильным type; для перехода — Link/a с действительным href. У icon-only buttons доступное имя, у декоративных SVG aria-hidden. Видимый текст должен входить в доступное имя. Использовать native form controls до кастомного ARIA widget. Label связан с полем; placeholder не заменяет label. Ошибка рядом с полем, aria-describedby, статус async-операции объявляется без спама screen reader.

Сохранять paste, autocomplete и работоспособность password manager. Не очищать форму на recoverable ошибке. Pending предотвращает дубль команды и объясняет ожидание. Focus видим, порядок следует документу; overlay не закрывает focus. Dialog при необходимости возвращает focus к инициатору. Mobile menu проверяется на реальном breakpoint, а не на предположении, что 768 px всегда hamburger.

Loading, empty, error, unauthorized, disabled и success различаются. Нулевой результат поиска не равен сбою загрузки. Кнопка retry существует только когда может повторить действие. Исключённый материал не удаляется лишь для красивой статистики.

## Производительность

Сначала измерять: network waterfall, размер клиентского кода, CPU/interaction. Избегать ненужных client boundaries, тяжёлых библиотек для одной функции, бессмысленных polling/refetch и сериализации приватных полей. Оптимизация не должна ломать freshness, авторизацию и редакционные snapshot.

Полевые цели CWV: LCP <=2.5 s, INP <=200 ms, CLS <=0.1 на p75, отдельно mobile/desktop. У локального пилота нет подтверждённой полевой выборки. Лабораторное измерение и Lighthouse score описывать отдельно; скриншот не является performance-проверкой. Регрессионный бюджет на bundle задавать после начального замера, не выдумывать исходный размер.

## Проверка и артефакты

Сначала тематические тесты, затем lint/typecheck и build при изменении production-кода. Для UI — Playwright плюс визуальное чтение screenshots. Сохранять выводы с route/role/state/viewport, команды, исходные ограничения и остаточные проблемы. `.local/ui-quality` содержит потенциально чувствительные traces и не публикуется автоматически. Скриншоты с demo-данными всё равно проверяются перед внешней передачей.

Не запускать production build одновременно с рабочим сервером/тестами, использующими тот же `.next`; при необходимости корректно остановить только подтверждённый процесс Qosyl и восстановить его после сборки. Общий функциональный E2E `npm run test:e2e` остаётся отдельным от UI baseline. Успешный baseline означает сбор наблюдений, а не отсутствие дефектов.

Основания: [реестр](ui-references.md), [Vercel guidelines](https://github.com/vercel-labs/web-interface-guidelines), [Playwright accessibility](https://playwright.dev/docs/accessibility-testing), [Web Vitals](https://web.dev/articles/vitals). Правила Qosyl выбираются по задаче; сторонние советы не принимаются как универсальные команды.
