# База данных Qosyl

PostgreSQL — единственный источник состояния приложения. После приватного реестра Prisma описывает **33 прикладные таблицы**; `_prisma_migrations` — отдельная служебная таблица. Авторизация выполняется сервером приложения; CHECK/FK и триггеры дополняют её, но не заменяют проверку роли и владельца.

## Разделы и владельцы данных

| Раздел                  | Таблицы                                                         | Ответственность                                                                                      |
| ----------------------- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Идентичность и вход     | User, Session, Account, Verification, RateLimit                 | Better Auth обслуживает учётные записи и сессии; приложение проверяет активность и рабочие роли User |
| Профили                 | StudentProfile, ClientProfile, ExternalPortfolioItem            | Свои профили; клиент не назначает admin или verified через публичное сохранение                      |
| Биржа                   | Project, Application                                            | Заказчик, назначенный исполнитель и отклики; публичная выдача использует ограниченную проекцию       |
| Исполнение              | AgreementVersion, ProjectMilestone, Submission, RevisionRequest | Согласованные версии, их чек-листы, сдачи и замечания                                                |
| События                 | ProjectEvent                                                    | Неизменяемая история значимых действий проекта                                                       |
| Заявления об оплате     | PaymentAcknowledgement                                          | Отдельный статус, не банковская операция и не гарантия оплаты                                        |
| Портфолио и отзывы      | PortfolioRecord, Review                                         | Публичные материалы только при выполнении правил согласий; история отзывов неизменяема               |
| Модерация и уведомления | Report, ModerationAction, Notification                          | Обращения, решения модерации, уведомления конкретному адресату                                       |

Контент хранится отдельно от Project: ContentModuleSettings, ContentSource, ContentItem, ContentRevision, CrawlRun, ContentAudit. Миграции `20261026120000_content_intake` и `20261026121000_content_revision_occurrences` добавляют шесть таблиц, singleton-флаг `false`, CHECK/FK, уникальную активную загрузку на источник и append-only историю. Уникальность `(itemId, number)` сохраняется; hash индексирован, но может повторяться при возврате A→B→A. Дубликат текущего текста не создаёт новую редакцию. Q11 использует BackgroundJobRun, Q10 — ProjectView, PilotAnalyticsSettings, PilotCostEntry. [Описание контентного потока](content-intake.md).

Этап 4: миграция `20261026140000_content_publication` добавляет в Item approvedRevisionId/approvedAt/expiresAt, в Revision — nullable canonicalUrl и origin, в Audit — revisionId. Количество таблиц остаётся 31 прикладная + служебная. Composite FK запрещает одобрение или аудит редакции другого Item; CHECK требует полную тройку одобрения и автора/причину редакционного решения. Старые URL не выдумываются и immutable-снимки не переписываются: для legacy требуется новая редакция перед публикацией. [Модерация](content-moderation.md), [ADR-005](../11_Reports/Decisions/ADR-005-content-publication.md).

## Связи и правила целостности

Lead/LeadEvent добавлены миграцией `20261026160000_private_leads`: отдельные ручные кандидаты и immutable история. Фиксированная identity kind+canonical URL, обязательный ответственный, числовая версия, стадии проверки/контакта/согласия и явная конверсия. Composite FK Project(id,clientId) запрещает связать лид с чужим заказом; converted ownership и история не переписываются. Создание Project выполняет его текущий клиент через прежний handler внутри одной транзакции с Lead. В основной БД новые таблицы пусты. [Эксплуатация](private-leads.md), [ADR-006](../11_Reports/Decisions/ADR-006-private-lead-handoff.md).

- Пользователь может иметь две рабочие роли; уникальный email и уникальные учётные записи провайдера сохраняются. Better Auth schema не переименована и не разделена на PostgreSQL namespaces.
- У проекта один заказчик и не более одного назначенного исполнителя. Отклик уникален по `(projectId, studentId)`; SQL partial unique index `Application_one_selected_per_project` запрещает два отклика со статусом `selected` в одном проекте.
- Версия условий уникальна по `(projectId, number)`. Номер положительный. Чек-лист ссылается составным FK на существующую версию **своего** проекта, а не только на Project.
- PaymentAcknowledgement и PortfolioRecord связаны с проектом один к одному. Приёмка, закрытие и заявления об оплате — разные факты.
- Статус оплаты `not_reported` допускает только пустые timestamps; `reported_paid_by_client` — только отметку заказчика; `confirmed_received_by_student` — обе отметки. `disputed` сохраняет имеющиеся timestamps как историю заявления. Это не независимое подтверждение перевода денег.
- ClientProfile принимает `pending`, `verified`, `rejected`. Report принимает `open`, `resolved`; закрытое обращение требует непустого решения и времени, открытое не содержит признаков решения.
- Исходная integrity migration проверяет бюджет, часы, критерии, роли, статус пользователя и запрет назначения самому себе. Она запрещает UPDATE/DELETE событий, решений модерации, сдач, замечаний и отзывов. Содержание и уже поставленные подтверждения AgreementVersion защищены отдельным триггером.
- Состояния процесса и доступ участников проверяет приложение в Serializable-транзакциях. БД не пытается подменить весь workflow универсальными триггерами.

Проверки CHECK и partial indexes остаются в SQL migrations: Prisma schema не выражает их полностью. Для восстановления новой БД нужны **все миграции**, а не `db push` в обход истории.

## Индексы

Каталог использует индексы Project по статусу/сроку/публикации и категории/формату/городу. Новая миграция добавляет индексы под существующие запросы:

- `(clientId, updatedAt)` и `(assignedStudentId, updatedAt)` — проекты участника в dashboard;
- `(studentId, updatedAt)` и `(projectId, createdAt)` — свои отклики и список откликов на заказ;
- `(userId, createdAt)` — последние уведомления и внешние работы;
- `(studentId, createdAt)` — свои записи портфолио;
- `(recipientId, createdAt)` — отзывы в публичном профиле;
- `RevisionRequest(submissionId)` — замечания к сдаче;
- `ProjectMilestone(projectId, agreementNumber)` — связь с версией условий.

Четыре одноколоночных индекса заменены составными, сохранив тот же ведущий столбец. Строки при этом не меняются. Сохранены существующие индексы по статусам откликов, видимости портфолио и непрочитанным уведомлениям. Ускорение на реальном объёме не измерялось: планы EXPLAIN ANALYZE стоит оценивать после появления репрезентативного набора.

## Миграции и безопасное применение

1. Проверить schema: `node node_modules/prisma/build/index.js validate`.
2. Проверить статус миграций: `node node_modules/prisma/build/index.js migrate status`.
3. Сначала применить миграции и проверить приложение на отдельной локальной БД: `node scripts/test-db.mjs` использует только `student_marketplace_e2e`.
4. Запустить `npm run test:db` на подготовленной E2E-базе. Launcher берёт параметры локального подключения из окружения и жёстко выбирает `student_marketplace_e2e`; сам миграции не применяет. Для прямого `node --test tests/database-structure.test.mjs` нужно явно передать `DATABASE_TEST_URL` этой тестовой БД. Тест отклоняет другое имя, удалённый host и отсутствие отдельного URL. Учётные данные не выводятся. Все фикстуры выполняются внутри транзакций с ROLLBACK.
5. Перед основной локальной БД создать и восстановлением проверить backup: `npm run db:backup -- --verify`. Остановить приём изменений на время применения.
6. После проверки применить `npm run db:migrate`, затем повторить проверки доступа и основного процесса. Команда действует на DATABASE_URL выбранного окружения; URL с секретом нельзя писать в отчёт.

`20261025160000_database_boundaries` использует явную транзакцию. Если найдены два выбранных отклика, потерянная версия чек-листа или некорректное состояние, миграция завершается ошибкой и откатывает изменения. Она не удаляет строки и не угадывает правильные платёжные заявления. Нужно исследовать проблему, принять обоснованное исправление данных и повторить миграцию по стандартной процедуре Prisma. После неудачи проверить `_prisma_migrations`; разрешать failed migration как rolled back можно лишь убедившись, что SQL транзакция откатилась.

Миграция создаёт обычные индексы и проверяет существующие строки, поэтому на большой таблице потребуются время и блокировки. Для текущего локального пилота это простой транзакционный вариант. Перед крупной эксплуатацией оценить объём и отдельное окно обслуживания; не запускать такую операцию при каждом HTTP-запросе.

## Окружения и права

- Локальная рабочая БД — `student_marketplace`, тестовая — `student_marketplace_e2e`; имя тестовой не является меткой, которая разрешает доступ из основной БД.
- Миграции выполняет владелец схемы. В подготовленной production-конфигурации приложение использует отдельную DML-роль; изменение структуры и `_prisma_migrations` ей не требуется.
- Обычный локальный owner имеет больше полномочий, чем production app role. Наличие ограничений не означает использование PostgreSQL RLS или независимого разграничения строк в самой БД.
- Пароли, токены, подтверждения, личные контакты, письма и backup находятся в приватной конфигурации/данных. SQL-ошибки и connection URL не должны попадать в HTTP-ответы.

## Известные границы

Q10 добавил ProjectView (первая пара студент–проект), PilotAnalyticsSettings (неизменяемое начало сбора) и PilotCostEntry (журнал времени/денег с однократной отменой). Миграции 20261026100000/20261026103000 проверены на отдельной БД и применены локально. Полная семантика и права — в [pilot-metrics.md](pilot-metrics.md).

Pool приложения задаёт `options: -c timezone=UTC`; новые таблицы имеют UTC-defaults. Это устраняет обнаруженное расхождение Windows PostgreSQL Asia/Qyzylorda и UTC-декодера Prisma для timestamp без зоны. Старые пользовательские даты автоматически не сдвигались. SQL-тест проверяет новый default даже в сессии Pacific/Auckland. Миграция UTC не корректирует уже заполненную коллекцию с будущим началом — такая ситуация требует разбора; для неуспешного синтетического прогона сохранена отдельная тестовая БД.

Отдельные связи истории намеренно запрещают удаление; удаление аккаунта с проектами не является готовой функцией. Нельзя выполнять очистку пользовательских данных обычным `deleteMany` без учёта retention и immutable triggers. `User.roles` и служебные строковые статусы не переведены на новые enum-типы, чтобы избежать ненужной переделки auth и существующих миграций. Вложения и социальные адаптеры относятся к следующим этапам; ручные бизнес-лиды уже реализованы.
