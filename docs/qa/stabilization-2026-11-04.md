Проверка исправленного продукта выполняется из `.local/stabilization-2026-11-04/workspace/`: отдельная копия исходников, отдельный PostgreSQL-кластер и новые автоматически именуемые тестовые БД. Исходные пользовательские изменения не сбрасывались.

## Проверка пределов через настоящий прокси

[scripts/test-proxy-body-limits.mjs](../../scripts/test-proxy-body-limits.mjs) требует явный абсолютный путь `CADDY_BIN`. Он ничего не скачивает и не устанавливает. Для текущей проверки использован официальный Caddy v2.11.8; SHA512 архива сверена. Бинарник и подтверждение проверки находятся в игнорируемом `.local/proxy-validation-tools/v2.11.8/`.

Пример из корня репозитория, после установки доверенного локального Caddy:

```powershell
$env:CADDY_BIN = (Resolve-Path -LiteralPath '.local/proxy-validation-tools/v2.11.8/caddy.exe').Path
node scripts/test-proxy-body-limits.mjs
```

При другом расположении нужно указать собственный существующий абсолютный путь. Helper адаптирует полный Caddyfile репозитория и подменяет только адреса слушателя/тестового upstream, использует loopback и отдельные каталоги конфигурации/данных. Превышение предела на один байт, chunked-тела, соседние пути, query string, PATCH/DELETE и сохранение обычного JSON-предела входят в 19 HTTP-проверок. Это проверка прокси с синтетическим upstream, а не production-загрузка и не проверка всей цепочки авторизации приложения.

В первом диагностическом запуске Caddy создал `autosave.json` в пользовательском AppData. Совпадение точной синтетической конфигурации и времени создания было проверено; удалён только созданный тестом файл, без рекурсивной очистки и удаления другой конфигурации. Итоговый helper задаёт изолированные `XDG_CONFIG_HOME`/`XDG_DATA_HOME` до вызовов Caddy. Санитизированное доказательство — `.local/proxy-validation-tools/autosave-cleanup.json`.
