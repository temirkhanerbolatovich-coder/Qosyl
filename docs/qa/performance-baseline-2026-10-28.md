# Базовое измерение поиска проектов по релевантности — 28.10.2026

## Цель и границы

Зафиксировать локальную отправную точку для масштабирования сортировки каталога; код приложения, действующая БД и публичный сайт не изменялись. Использована отдельно созданная синтетическая PostgreSQL-база `student_marketplace_e2e_ui_27238d6d52ec` на выделенном локальном кластере Qosyl (`127.0.0.1:55432`), с применёнными существующими миграциями. Таблицы содержат только одного синтетического заказчика и синтетические проекты, без реальных пользовательских данных. База оставлена для проверки. Сервер PostgreSQL при этом общий с локальным кластером, поэтому измерения не являются полностью независимыми по аппаратным ресурсам.

## Метод

Прямой вызов существующей серверной функции `publicQueries` в отдельном Node-процессе с `--conditions=react-server --import tsx`; HTTP, браузер, Next.js и сеть до внешнего хоста не измерялись. Гость, `view=catalog&sort=relevance&q=Benchmark`, страница 1: все строки соответствуют запросу, возвращаются первые 30. Данные добавлялись последовательно до 100, 1 000, 10 000 строк; перед каждой серией выполнен `ANALYZE "Project"`, три прогрева и 15 последовательных вызовов. Проверялись total и количество записей. P50 — восьмое значение, P95 nearest-rank для n=15 совпадает с максимумом; это слишком мало для устойчивого хвостового процентиля. Heap — моментальный `heapUsed` после серии, не пик, не RSS и не оценка потребления каждого запроса: сборщик мусора не фиксировался.

Среда: Windows, Intel Core i5-12450H, 12 логических процессоров, 16 886 784 000 байт RAM; Node v24.12.0, установленный клиент psql 18.4. Конкурирующая фоновая нагрузка не контролировалась; Node/Prisma и локальный PostgreSQL использовали один компьютер. Не измерялись SQL-планы, профиль авторизованного студента, разная селективность, параллелизм, большой размер полей и сеть.

Источники: `src/server/marketplace/queries/public.ts`, `src/lib/catalog-query.ts`; исполняемый harness и результат в игнорируемых `.local/performance-baseline.mts` и `.local/performance-baseline-20261028.json`. Это прямое измерение серверной функции, не нагрузочный тест и не оценка реальной эксплуатации. Подтверждается рост времени в данных условиях; вывод о приемлемости, предельной ёмкости, потреблении памяти на запрос и необходимости немедленной оптимизации без требований и повторного измерения делать нельзя. Реальные устройства, малую VM, HTTP и concurrent нагрузку следует проверять отдельно по согласованному сценарию и порогам.
