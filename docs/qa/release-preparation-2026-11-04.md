## Порядок обновления

1. Дождаться успешного CI точной публикуемой ревизии и сохранить её hash. На машине разработчика доступен Docker 29.8.0, Linux x86_64; образ следует собирать вне Oracle VM. Сборка на VM с 1 ГиБ RAM запрещена процедурой проекта.
2. Собрать Linux amd64 image из точной ревизии с действующим `.dockerignore`, проверить содержимое, миграции и runtime без production-секретов. Затем сохранить image-архив, сверить SHA256 после передачи и загрузить на VM. Текущая подготовка контейнера ещё расследует ошибку установки optional SWC; этот документ не объявляет новый image готовым.
3. До смены app сохранить текущий image ID/отдельный rollback tag и копии Compose/Caddyfile; сохранить production `.env`, Search Console directory и существующие volumes. Сделать ещё один свежий backup, если после проверенного прошло время или появились записи.
4. Подготовить source/compose из того же release. Выполнить `compose config --quiet` без печати интерполированных секретов, использовать основной Compose вместе с `compose.small-vm.yml`, не выполнять build на VM. Проверить предел POST аватара 2 МиБ, прежние пределы JSON и проектных файлов.
5. В согласованном коротком окне запретить новые записи приложения, выполнить штатный migration-контейнер с owner-ролью и повторным ограничением app-role. Не выполнять seed, reset, `down -v` или массовый prune. Проверить 21 успешную миграцию и отсутствие failed/pending состояния.
6. Переключить только app и необходимую конфигурацию proxy. Не перезапускать VM, PostgreSQL или TimScheduleBot без отдельной необходимости. Проверить health, гостевые страницы, отсутствие demo, регистрацию, новые API с отказом гостю, сохранность количества критичных записей и состояния соседнего бота. Реальные SMTP/OAuth-сценарии имеют отдельную приёмку.

Все команды миграции/переключения требуют точного release image и финального выбора координатора; этот этап их не выполнял.

## Подготовленный сценарий переключения

В `.local/release-2026-11-04/deploy-reviewed-release.py` подготовлен серверный сценарий с обязательным `--apply`. Выполнены только AST-проверка Python и безопасный `--help` на серверном Python; production-переключение этим сценарием ещё не выполнялось. Перед запуском координатор проверяет окончательный текст и независимое review, принимает image и передаёт полные commit/image ID, release-source и SHA256 манифеста файлов.

Манифест имеет форму `{"commit":"<полный hash>","files":{"путь/внутри/release":"<sha256>"}}`. Он создаётся из точной архивированной Git-ревизии, а его ожидаемая контрольная сумма передаётся отдельно. Сценарий проверяет полный image ID и OCI label `org.opencontainers.image.revision`, hashes перечисленных файлов, все 21 SQL-миграцию и обязательные Docker/package/Compose/Caddyfile. Секретные `.env` в новом source-каталоге запрещены; действующая production-конфигурация остаётся на сервере.

Глобальная блокировка не допускает двух одновременных переключений. Отдельный marker коммита запрещает повторный или автоматический resume незавершённой попытки: оператор должен сначала прочитать сохранённый этап и принять решение. В журнал попадает только ограниченная проекция docker inspect (image ID и состояние), без `Config.Env`.

Переход включает временный HTTP 503 с Retry-After и сохранением Search Console-файлов, остановку только app/его workers, новый backup уже замороженных записей, его SHA256/`pg_restore --list` и реальное восстановление в ещё одну уникальную базу. Её нормализованные строки сравниваются с замороженным snapshot; затем временная база удаляется. После штатной миграции проверяются 21 запись истории и сохранность старых данных. Новый app пересоздаётся с `--no-deps --no-build`, проходит внутренний GET-only smoke, и только затем открывается публичный доступ.

Обе конфигурации Caddy содержат `admin off`, поэтому reload API не включается и не используется. Файл перезаписывается с сохранением bind-mounted inode, а перезапускается только proxy-контейнер; сертификаты и volumes сохраняются. Краткое окно maintenance включает этот перезапуск. При ошибке сценарий старается сохранить/вернуть maintenance и оставляет private phase/log; он не восстанавливает рабочую БД и не возвращает старый app автоматически. Флаг возможного публичного доступа фиксируется до переключения консервативно, чтобы оператор не предполагал отсутствие новых приватных записей при частично успешном открытии.

## Ограничения отката

Прежний production image `sha256:8e4b90b1ab3c6b2ffe79493da8575a3ecaf06fcdde783a0e8674331093ea9969` сохранён на VM. Но обратное переключение старого приложения после новых записей кейсов небезопасно: старая версия публикует внешние работы без новых правил видимости и может разрушительно пересоздавать их при сохранении профиля.

Если новый app не прошёл smoke до разрешения записей, rollback возможен только после проверки отсутствия новых несовместимых данных. После разрешения новых private/draft кейсов предпочтительны режим обслуживания и исправление вперёд либо специально подготовленный rollback-код, сохраняющий фильтрацию и ID. Нельзя вслепую возвращать старый image или старый dump поверх новых данных. Аддитивные поля/таблица остаются до согласованного экспорта и решения о хранении; удаление столбцов не является частью оперативного отката.

Копия хранится на той же VM; внешнее независимое хранение остаётся открытым пунктом. Проверка не подтверждает восстановление после полной потери VM/IP, нагрузочную ёмкость, доставку писем, юридическую готовность или полноценный внешний pentest.
