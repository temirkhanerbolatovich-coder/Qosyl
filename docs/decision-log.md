> История технических решений. Текущий режим — локальная демонстрация по README; прежняя подготовка Oracle не подтверждает действующее облачное развёртывание. Решение о структуре проекта — в 11_Reports/Decisions/ADR-001-project-layout.md.

## 2026-10-25 — Qosyl и измерение пилота

Имя Qosyl применяется через существующий config, включая метаданные и письма. Имена БД и технические package ID сохранены: их смена не нужна для брендинга. Историческое ТЗ со срезом 42 ответов не переписывается; актуальный срез 45 описан в README и Qosyl.

Для первых результатов используется существующий неизменяемый журнал событий: один проект на этап, знаменатель — когда-либо одобренные реальные проекты. Нет новых внешних трекеров и фиктивных просмотров. Расчёт в памяти допустим для малого пилота; ограничение и переход к SQL описаны в docs/pilot-metrics.md. Это частичное выполнение этапа 2, не полная воронка.

## 2026-10-25 — исходное состояние и стек

В корне нет Git-репозитория и исходников приложения; есть опросник и исследование. Создаем приложение в корне, исходные материалы не изменяем. Стек: Next.js App Router + React + strict TypeScript, PostgreSQL + Prisma, Better Auth, Zod, Tailwind CSS, Lucide, Vitest/Playwright. UI непосредственно в коде. Название централизуется в конфигурации. После первоначального npm audit выбрана исправленная Prisma7.10.1 с PostgreSQL driver adapter (в6 найдены уязвимости зависимостей CLI); итоговый аудит проверяется отдельно. Не используем неподдерживаемые принудительные peer overrides для сокрытия уязвимостей.

## Локальный пилот и PostgreSQL

Используем настоящий изолированный PostgreSQL на loopback-порту 55432 с отдельным каталогом `.local/postgres`, не затрагивая установленную системную службу и ее данные. Предусматриваем Docker Compose для переносимого запуска. Локальные секреты генерируются и исключаются из Git. Публичное размещение не входит в текущую проверку: без почтового провайдера разрешен только явно включенный локальный режим, production start должен отказывать.

## Безопасные материалы

В P0 результаты передаются HTTPS-ссылками и текстом. Загрузка бинарных файлов откладывается до подключения закрытого хранилища, signed URL и сканирования. Ссылки не скачиваются сервером (нет SSRF), не встраиваются как HTML, приватные ссылки не выводятся в публичных проекциях.

## Формы и инструменты проверки

Формы используют нативные доступные HTML-поля и FormData, состояние отправки и ошибки React; валидация Zod выполняется на сервере. React Hook Form не добавлен: текущие короткие формы не требуют отдельной библиотеки управления состоянием. ESLint9.39.5 выбран из-за заявленных peer-диапазонов плагинов текущего eslint-config-next; переход на10 откладывается до их совместимости. Эта версия уже отмечена npm как неподдерживаемая, что зафиксировано как долг инструментария; npm audit проверяется отдельно и не доказывает отсутствие всех рисков.

## Объем и доказательства

Демо-данные имеют флаг `demo`; Oxford Team — отдельный закрытый пример без откликов, не партнер. Платежи вне площадки, статусы являются заявлениями участников. Реальная приемка и оба закрытия определяют completed; подтверждение оплаты хранится отдельно. Публичное портфолио требует совпадающего согласия обеих сторон на конкретную версию обезличенного материала. Никаких искусственных KPI и реальных персональных данных из опроса.

## Контракты и доступ

JSON `/api/platform?view=...` для чтения и POST `/api/platform` с дискриминатором action для изменений; Zod на сервере, `{data}` при успехе, `{error}` при отказе. Один явно перечисленный action handler уменьшает дублирование guards и транзакций в MVP; это не универсальный обработчик произвольных таблиц. Изменения разрешены только из того же Origin с авторизованной сессией; role, ownership и state проверяются сервером внутри сериализуемой транзакции. Админ назначается только локальной серверной командой/seed, не формой. Аудит добавляется вместе с изменением, исторические записи защищены также триггерами БД.

## ADR-001: Изолированное развертывание закрытого пилота

Статус: принято для подготовки, облачный запуск не подтвержден. Дата:25.10.2026.

Контекст: владелец выбрал новую Oracle Always Free VM и DuckDNS, потребовал сохранить работающий TimScheduleBot. Рассмотрены запуск на старой VM, удаление старых ресурсов ради новой VCN и отдельная VM с отдельной подсетью в существующей VCN.

Решение: отдельная A1 VM, production Docker Compose с PostgreSQL18, Caddy HTTPS и первоначальным Basic Auth, без demo; миграции выполняются владельцем БД, приложение использует отдельную DML-роль. Токен DuckDNS не обязателен для основного запуска: DNS можно установить в dashboard, updater включается отдельным профилем. Почтовый провайдер — Oracle Email Delivery по выбору владельца.

Причины: не останавливаем бота, не смешиваем данные проектов и не удаляем восстановимые сервисы ради квоты VCN. Отдельная роль ограничивает последствия ошибки приложения; переносимый Compose позволяет повторить запуск и восстановление. Начальный дополнительный вход ограничивает аудиторию до приемки.

Последствия и риски: subnet использует существующую VCN, поэтому нельзя расширять общие сетевые правила без проверки влияния на старые VM; требуется реальная проверка Linux/ARM образа, прав БД, SMTP, backup/restore и TLS. Oracle может отказать из-за отсутствия свободных A1 хостов (такой отказ получен); это не разрешение переходить на платную конфигурацию или удалять старые AMD VM. Публичное самообслуживание до готовности пилота не включается.

Дальнейшая работа: завершить создание VM при доступной Always Free емкости, проверить серверный запуск и восстановление, затем провести закрытый пилот. Снятие Basic Auth и смена архитектуры решаются по фактическим результатам пилота.

## ADR-002: Локальная демонстрация до финансирования

Статус: принято владельцем. Дата:25.10.2026. Приоритет над сроками облачного запуска ADR-001.

Контекст: Oracle отказал в создании бесплатной A1; владелец выбрал закончить ТЗ и показать продукт на собственном компьютере, покупать сервер только после финансирования. Варианты: ждать облако, менять хостинг или завершить локальную демонстрацию с тем же приложением и PostgreSQL.

Решение: production-сборка Next.js на loopback, отдельный локальный PostgreSQL55432, существующий безопасный локальный почтовый flow; один запуск через CMD/npm, резервирование custom dump и проверка восстановления в отдельную временную БД. Публичные настройки не ослабляются. Облачные исходники сохраняются для будущего переноса.

Причины и последствия: ТЗ прямо допускает локальную готовность и dev-почту; серверные роли, реальные транзакции и данные остаются настоящими. Демонстрация не зависит от наличия свободной облачной VM. Зависимости и PostgreSQL нужно установить заранее; компьютер является единственной точкой отказа, поэтому перед выступлением необходимы проверенная копия на другом носителе и репетиция. Внешние ссылки требуют интернета. P1, реальные сделки, публичный пилот и доставка email не становятся завершенными из-за локального показа.

Дальнейшая работа: закрыть локальную приемку, провести демонстрацию; при финансировании вернуться к отдельному этапу сервера, SMTP, HTTPS и эксплуатации.
