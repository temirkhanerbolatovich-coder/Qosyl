# Архитектура MVP

Опциональный Q24: admin → `/api/admin/leads/threads` → серверный read-only клиент фиксированного Threads keyword_search → временный preview → явный выбор/форма → прежний `createLead`. Секрет только в окружении; общий RateLimit ограничивает попытки и паузу 429. Новых таблиц/worker нет; при выключении или отказе работают ручной реестр и биржа. [Решение ADR-007](../11_Reports/Decisions/ADR-007-threads-search-preview.md), [эксплуатация](threads-search.md). Реальный доступ Meta ещё не подтверждён.

Приложение реализует один основной процесс: заказчик публикует ограниченную задачу, модератор проверяет ее, студент откликается, стороны согласуют условия и подтверждают результат. Это локальный пилот 18+, а не платежный сервис.

## Компоненты

- Next.js App Router и React: RU-интерфейс, публичный каталог, личные кабинеты, рабочая область и административные экраны.
- Better Auth: email/пароль, хеширование паролей, cookie-сессии, восстановление доступа. Prisma adapter хранит пользователей, учетные записи, сессии и одноразовые проверки в PostgreSQL.
- JSON API: `/api/platform`, `/api/profile`, `/api/admin/content` с историей, `/api/content/posts`, `/api/admin/leads` с историей, `/api/leads` и `/api/auth/*`. Проверки доступа выполняет сервер, клиентские ограничения не считаются защитой.
- Prisma7.10.1 с `@prisma/adapter-pg`: типизированные запросы, внешние ключи, индексы, уникальные ограничения и сериализуемые транзакции. Конфигурация подключения — `prisma.config.ts` и DATABASE_URL; состояние живет в настоящем PostgreSQL, перезапуск Next.js его не сбрасывает.
- Vitest и Playwright: проверки переходов и прав, HTTP-сценарии на настоящей базе и браузерные проверки интерфейса.

## Организация API и серверных модулей

HTTP-обработчики `src/app/api/platform/route.ts` и `profile/route.ts` отвечают за протокол: origin, JSON, ограничения размера, получение сессии, ответ и обработку ошибок. Они не выполняют запросы к таблицам профиля или переключение бизнес-действий.

```text
src/app/api/                       HTTP-адаптеры и отдельный Better Auth endpoint
src/server/api/http.ts             единые ответы, ошибки, проверка origin и JSON
src/server/marketplace/index.ts     явная маршрутизация 30 команд / 10 видов чтения
src/server/marketplace/commands/    projects, applications, work, portfolio, moderation, notifications
src/server/marketplace/queries/     public, account, admin
src/server/marketplace/shared.ts    guards владельца/участника, аудит, уведомления, rate-limit
src/server/marketplace/projections.ts  разрешённые публичные поля Prisma select
src/server/profile/service.ts      собственный профиль и транзакционное обновление
src/server/pilot/                  запись просмотров, формулы и административный журнал затрат
src/lib/catalog-query.ts           проверка фильтров и календарной даты
src/lib/db.ts                      единственный клиент Prisma для серверного приложения
```

Серверные entrypoints и клиент БД помечены `server-only`. Чистые валидаторы и функции проверки переходов доступны отдельно для тестов и форм. `src/lib/marketplace.ts` оставлен как совместимый экспорт; фактическая реализация находится в server. Общий HTTP helper возвращает `{data}` либо `{error,code,fields?}` с `Cache-Control: private, no-store`. Operational health и ответы Better Auth сохраняют собственные форматы.

Публичные запросы используют явные `select`. Раздел account предназначен текущему пользователю и участникам конкретного заказа; admin имеет отдельную проекцию очередей и не получает приватный адрес/контакт проекта. Администратор не становится участником рабочей области автоматически. Команды внутри Serializable-транзакции повторно читают статус/роли пользователя и проверяют принадлежность сущности и допустимое состояние; HTTP-роль сама по себе не заменяет эти проверки.

Контракт: [OpenAPI](api/openapi.json), [правила обновления](api/README.md). Границы БД и миграции: [database.md](database.md). Причины сохранения существующих URL и общей БД: [ADR](../11_Reports/Decisions/ADR-002-api-database-boundaries.md).

## Публичные и приватные данные

Приватные кандидаты находятся в `src/server/leads` и Lead/LeadEvent. `/api/admin/leads` и `/{id}` — admin-only, `/api/leads` — минимальная передача конкретному client и его явная конверсия. Социальных вызовов здесь нет. Конверсия повторно проверяет владельца/согласие/срок/версию и вызывает существующий projectsCommands(createProject) в общей транзакции с привязкой и событием. Получается прежний draft и прежняя модерация, без новой разновидности Project. [Поток и ограничения](private-leads.md), [ADR-006](../11_Reports/Decisions/ADR-006-private-lead-handoff.md).

Модуль возможностей отделён от биржи: `src/server/content` → шесть собственных таблиц, `/api/admin/content` и история `/api/admin/content/{id}` → только admin. `/api/content/posts` → явная публичная проекция одобренной редакции, максимум шесть актуальных материалов включённых источников. Публикация требует отдельного решения; изменение источника возвращает материал на проверку. `npm start` владеет web и двумя worker; контентный worker получает lease в короткой транзакции, выполняет ограниченный HTTPS-запрос вне неё и повторно проверяет флаги перед сохранением. Он также архивирует истёкшие публикации; публичный фильтр сроков работает независимо. Модуль и источники изначально выключены. Главная читает карточки отдельно и скрывает блок при отказе. [Сбор](content-intake.md), [модерация и лента](content-moderation.md), [ADR-004](../11_Reports/Decisions/ADR-004-content-intake.md), [ADR-005](../11_Reports/Decisions/ADR-005-content-publication.md).

Публичный каталог выводит только разрешенную проекцию актуальных опубликованных заказов. Точные места, контакты, отклики, результаты, внутренний аудит и платежные заявления не являются общедоступными данными. Рабочая область доступна участникам, административные функции требуют серверной роли admin.

Профиль студента публикуется по его настройке. Самостоятельные внешние работы имеют уровень self-reported. Запись client-confirmed появляется после приемки; публикация ее конкретного содержания требует согласия обеих сторон. Ссылки на приватные результаты не копируются в публичное портфолио автоматически.

## Поток заказа

1. Автор создает draft и отправляет pending_moderation.
2. Администратор публикует или возвращает на доработку с причиной.
3. Студенты отправляют бесплатные отклики. Назначение одного исполнителя закрывает конкурирующие отклики.
4. Согласование сохраняет снимок условий и независимые подтверждения сторон. Без обоих подтверждений сдача результата запрещена.
5. Исполнитель сдает результат; заказчик принимает либо фиксирует замечания по согласованным критериям. Новые сдачи и версии не перезаписывают историю.
6. Приемка дает accepted. Два подтверждения закрытия дают completed. Заявления об оплате хранятся отдельно; completed не доказывает факт оплаты.

Существенные изменения и аудиторские события записываются вместе. API не предоставляет редактирование или удаление истории задним числом. Вторая миграция добавляет CHECK-ограничения и триггеры запрета изменения событий, модерации, сдач, правок и отзывов. Для соглашения можно заполнить ранее пустое подтверждение; содержание, номер и уже записанные подтверждения неизменяемы. Чек-лист связан с номером версии: при согласовании новой версии создаются ее пункты, прежние сохраняются.

При назначении точные адрес и контакт скрыты от исполнителя во всех ответах до двустороннего согласования. Каждый еще не согласованный снимок новой версии редактируется в выдаче независимо от наличия прежних согласий. Предложение исполнителя не стирает скрытые контактные поля заказчика. Подтверждение условий содержит id версии; согласие на портфолио содержит timestamp просмотренной версии, поэтому устаревший экран не может подтвердить новое содержание.

Каталог фильтруется на сервере, по30 записей на странице. Релевантность:3балла за совпадение запроса с заголовком и1за каждый совпавший выбранный/профильный навык, без учета числа прежних заказов. Для сортировки всего набора пилота читаются только id/заголовок/навыки; при росте каталога этот шаг следует перенести в SQL или поисковый индекс.

## Внешние системы и запуск

Основной процесс не требует внешних AI, банковских API или CRM. Сервер не загружает пользовательские URL и не исполняет содержимое ссылок. В P0 используются текст и безопасные ссылки; бинарные вложения отложены.

Локальный PostgreSQL запускается отдельно от существующей системной службы в `.local/postgres` на `127.0.0.1:55432`. Этот каталог, `.env`, локальный почтовый ящик и зависимости исключены из Git. Docker Compose предусмотрен как альтернативный способ запуска базы.

Без почтового провайдера используется только явно включенный локальный режим: письма восстановления/проверки доступны владельцу файловой системы в `.local/mail`, не через HTTP. Публичное размещение требует настоящей почты, HTTPS, секретов, резервного копирования, мониторинга и правовой проверки документов. Оно не подтверждается локальными тестами.
