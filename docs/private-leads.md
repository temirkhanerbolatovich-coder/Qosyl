# Приватные лиды и обсуждения

Реализован ручной контур этапа 5: кандидат → проверка → ручной контакт → запись согласия → самостоятельный черновик заказчика. Найденный пост не считается заказом, не становится публичной возможностью и не увеличивает показатели биржи. Отдельно добавлен [опциональный Threads search preview](threads-search.md), выключенный до настройки доступа. Автоматических сообщений нет.

## Администратор

Путь: admin → **«Лиды и обсуждения»**.

1. Добавить запрос бизнеса или тематическое обсуждение. Нужны HTTPS-оригинал, название источника, заголовок, краткая суть, ответственный администратор и срок внутренней актуальности. Начальный срок формы — предложение оператору, а не дедлайн внешнего события; сервер допускает до 90 дней.
2. Проверить оригинал вручную и записать основание. Программа не открывает источник и не проверяет полезность запроса самостоятельно.
3. При уместности связаться с человеком вручную и записать итог. Кнопка сохраняет запись о совершённом человеком действии; она ничего не отправляет.
4. По бизнес-запросу записать, кто, когда и на какую передачу согласился, и указать ID действующего зарегистрированного заказчика. Он увидит только краткое описание и оригинал, без внутренних заметок и основания согласия.
5. Если получен отказ — зафиксировать отказ; если материал неактуален — архив. До создания заказа передачу можно отозвать. Изменить уже созданный заказ через реестр нельзя: им управляет его владелец обычными средствами биржи.

Все активные администраторы видят реестр; назначение ответственного — операционная ответственность, а не отдельная приватная область одного администратора. Список вариантов показывает до 100 активных администраторов и заказчиков без email. Для передачи можно ввести известный ID заказчика напрямую; сервер проверяет его роль и активность.

## Стадии и история

| Стадия                          | Допустимый следующий шаг                                                                                           |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Новый (`new`)                   | Уточнить описание/срок, назначить ответственного, проверить, заметка, отказ/архив                                  |
| Проверен (`verified`)           | Записать результат ручного контакта, заметка, отказ/архив, возврат на проверку                                     |
| Контакт записан (`contacted`)   | Для бизнес-запроса — запись согласия; для обсуждения — заметки и итог, без создания заказа                         |
| Согласие записано (`consented`) | Только указанный заказчик создаёт черновик; администратор может отозвать передачу, закрыть или вернуть на проверку |
| Отказ / архив                   | Только явный возврат человека с причиной начинает проверку заново                                                  |
| Черновик создан (`converted`)   | Связь с владельцем и заказом неизменяема; доступны заметки/смена ответственного, заказ живёт обычным workflow      |

Возврат на проверку сбрасывает текущие отметки проверки, контакта и согласия, но сохраняет прежние события. У просроченной записи нельзя продолжить проверку/контакт/согласие или создать черновик. При необходимости её возвращают на проверку и явно уточняют срок. Автоматического продления и сообщения человеку нет.

URL и тип фиксируют исходную идентичность и не изменяются. Заголовок, суть, название источника и срок можно исправить только в `new`; прежние значения сохраняются в событии. Из URL удаляются известные tracking-параметры и фрагмент, параметры идентичности сохраняются. Повтор `(kind, canonical URL)` возвращает существующую запись даже после отказа/архива, не возрождая её и не заменяя описание. Один URL может отдельно учитываться как бизнес-запрос и как обсуждение.

Каждое изменение требует текущую числовую expectedVersion; версия увеличивается на один, и в той же транзакции создаётся неизменяемый LeadEvent с автором, временем, причиной и деталями. Устаревшая форма получает 409. История читается по 20 событий на страницу. Физическое удаление записи, перезапись истории, замена исходного URL/автора создания и подмена владельца после конверсии запрещены БД.

Запись согласия — свидетельство оператора, не автоматическая верификация реального человека или юридическое подтверждение. Храните необходимый минимум, ссылку/описание основания, избегайте паролей и лишних персональных данных. Retention и процедура удаления персональных сведений требуют отдельного решения до реального масштабирования.

## Заказчик

В кабинете **«Мои заказы»** отображаются переданные этому аккаунту актуальные запросы и ссылки на уже созданные из них заказы. Раздел пуст и скрыт, если передач нет. Данные обновляются при открытии/фокусе окна и кнопкой «Обновить передачи»; любое действие дополнительно проверяется сервером.

«Проверить и создать черновик» открывает существующую форму нового проекта. Предлагаются только название и краткая суть. Бюджет, срок, результат и критерии пользователь указывает самостоятельно. Обязательна отметка, что это его задача и он подтверждает создание черновика. Привязка к leadId сама по себе ничего не создаёт.

Создание использует тот же transaction-level handler, что обычный `createProject`: draft, владелец из текущей сессии, прежние demo-правила и ProjectEvent. Связь Lead → Project и LeadEvent фиксируются в той же Serializable-транзакции. Следующие шаги — обычные отправка на модерацию, решение модератора и жизненный цикл биржи. Администратор без клиентской роли не может создать заказ вместо владельца, а другой клиент получает 404.

Повтор действительного идентичного запроса возвращает тот же projectId. Хеш строится по нормализованному обычному ТЗ; изменение бюджета или другого поля после успешной конверсии даёт 409 и требует открыть существующий заказ. При одновременных запросах один может получить конфликт, но второй черновик не появляется. Для повторов действуют обычная валидация ТЗ, активность аккаунта и подтверждение email вне локального режима.

## API и БД

| Маршрут                                                        | Назначение                                                                                                      |
| -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `GET /api/admin/leads?page=1&kind=business_request&status=new` | Только admin: до 20 записей, total по фильтрам, bounded operator/client options                                 |
| `POST /api/admin/leads`                                        | Только admin: десять ручных действий, JSON до 32768 байт                                                        |
| `GET /api/admin/leads/{id}?page=1`                             | Только admin: текущая запись и история по 20 событий                                                            |
| `GET /api/leads?page=1`                                        | Только client: до 20 своих актуальных consented передач или converted ссылок                                    |
| `POST /api/leads`                                              | Только client: leadId, expectedVersion, confirmation=true и project по общему projectFields; JSON до 65536 байт |

Все ответы private/no-store. POST требует точный Origin, JSON, повторную проверку текущих ролей/активности и подтверждение email вне локального режима. Ограничения: 60 успешных admin-операций/минуту и 30 клиентских операций/минуту; неуспешная транзакция откатывает изменения вместе со счётчиком. Число страницы 1–10000; неизвестные kind/status отклоняются.

Admin actions: createLead, editLead, assignLead, verifyLead, recordContact, recordConsent, revokeConsent, closeLead, reopenLead, addLeadNote. Все, кроме createLead, требуют leadId/expectedVersion. Причина — 10–2000 символов; recordConsent принимает evidence вместо reason и clientId. createLead возвращает `{data:{leadId,version}}`, остальные — ту же форму. Клиентская конверсия возвращает `{data:{projectId}}`.

Lead и LeadEvent — две отдельные таблицы. FK гарантирует существование автора/ответственного/клиента и связь только с проектом указанного владельца; CHECK описывает стадии, полную тройку согласия и конверсию. Source identity и версия защищены триггером; LeadEvent append-only. В текущей основной БД эти таблицы изначально пусты. Записи не входят в публичный API возможностей или метрики Project до реального создания проекта владельцем.

Клиентская проекция: id, version, status, title, summary, sourceName, sourceUrl, expiresAt, projectId. Не включает consentEvidence, conversionHash, заметки/события, акторов и чужие записи. Полный контракт — [OpenAPI](api/README.md), решение — [ADR-006](../11_Reports/Decisions/ADR-006-private-lead-handoff.md).

## Проверка и границы

После подготовки отдельной E2E-БД: `npm run test:leads`, `npm run test:db`, `npm test`, `npm run api:check`, `npm run lint`, `npm run typecheck`, `npm run build`, `npm run test:e2e`. Тесты реального PostgreSQL сохраняют синтетическую immutable-историю; SQL-проверки откатывают отдельные транзакции. Основная пользовательская БД не сбрасывается.

[Приёмка](qa/private-leads.md) отделяет unit, SQL, серверную интеграцию, настоящий HTTP/браузер и фактическую сохранность миграции. Postman CLI отсутствует; ручные обработчики не вызывают внешних сервисов. Отдельный опциональный поиск Threads описан выше. Контакт в тесте — явно синтетическая запись, не отправленное сообщение и не доказательство спроса.

Реализованы Q22/Q23 и ручная часть этапа 5. Q24 частично реализован как [официальный Threads search preview](threads-search.md) с явным выбором и сохранением кандидата. Приложение/токен Meta и реальный охват ещё не подтверждены. Нет фонового мониторинга, Telegram-коннектора, массовых комментариев, AI-рассылок или обработки настоящих обращений. Ручной контур работает независимо от доступности поиска.
