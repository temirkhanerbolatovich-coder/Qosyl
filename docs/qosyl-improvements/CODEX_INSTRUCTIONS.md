# Инструкция исполнителю (Codex)

Ты реализуешь подготовленный план. **Исследование, аудит и проектирование уже выполнены** — не повторяй их и не придумывай собственную архитектуру. Прочитай документы, возьми следующую задачу из [TASKS.md](TASKS.md), выполни её по [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md), проверь, отметь, отчитайся. Если документ и код расходятся — верь коду, остановись на этой задаче и опиши расхождение (§10).

## 1. Перед началом каждой сессии

1. Прочитай `AGENTS.md` (корень репозитория) — он обязателен и имеет приоритет над этим файлом.
2. Прочитай [README.md](README.md) этого каталога: ответы владельца на вопросы В-1…В-10 (раздел «Решения») — **задачи с ⚑ без ответа не начинай**.
3. `git status` и `git log -5`: чужие незакоммиченные изменения не трогай, не откатывай и не включай в свои коммиты.
4. Найди в TASKS.md первую невыполненную задачу без блокировки. Работай над **одной** задачей за раз.
5. Перед UI-работой прочитай `.agents/skills/ui-quality/SKILL.md`; по теме задачи — `.agents/skills/qosyl-architecture`, `qosyl-security`, `qosyl-qa`, `qosyl-performance`, `qosyl-review`, `qosyl-documentation`.
6. Next.js в проекте — 16.4 с изменённым API. Перед использованием любого API Next прочитай соответствующий раздел `node_modules/next/dist/docs/` (требование AGENTS.md).

## 2. Как работать с существующим кодом

**Сохранять (архитектурные решения, которые нельзя менять):**

- Слои: `src/app/api/*` (HTTP, origin, JSON, сессия) → `src/server/marketplace/index.ts` (маршрутизация команд/чтений) → `commands/*`, `queries/*` → Prisma. UI не ходит в БД, кроме существующих серверных страниц (`/talent/[id]`).
- Публичные данные — только через `src/server/marketplace/projections.ts` (явные `select`).
- Команды — в Serializable-транзакциях с повторной проверкой ролей/владения и аудитом (`shared.ts`).
- Формат ответа `{data}` / `{error, code, fields?}`; `Cache-Control: private, no-store`.
- Клиентская загрузка — `useData`, действия — `useAction` (`src/components/platform.tsx`); i18n — `useI18n().t(ru, kk)` или `useMarketplaceCopy().copy(ru)` со словарём KK.
- Токены — `src/lib/design-tokens.json` → `npm run ui:tokens`; HEX в CSS запрещены.
- Тестовая инфраструктура: изолированные БД, `test:ui`, `test:ui:baseline`, `test:e2e`.

**Принцип изменений:** минимальное изменение, которое выполняет критерии задачи. Переиспользуй существующие компоненты и CSS-классы (особенно решения этапов 0–2 из каталога возможностей: нижняя панель фильтров, чипы, `.detail-actions`, тосты). Новый компонент — только если существующий не подходит; новый файл — в `src/components/` или `src/lib/` по аналогии с соседями.

## 3. Что запрещено без согласования

Без явного письменного решения владельца (в README раздел «Решения» или в чате) **нельзя**:

1. Менять бизнес-правила: статусы и переходы заказа, модерацию, правила выбора исполнителя, согласия на портфолио, видимость профиля, скрытие контактов, правила оплаты.
2. Удалять существующие функции, маршруты, команды API, поля ответов.
3. Менять схему БД и создавать миграции (кроме задач с ⚑, получивших «да»). Перед любой миграцией — `npm run db:backup -- --verify`.
4. Добавлять npm-зависимости (UI-kit, анимации, state-менеджеры, CSS-фреймворки). Если без зависимости никак — остановись и обоснуй ссылками на официальную документацию и совместимость.
5. Подключать внешние/платные сервисы (AI, аналитика, карты, почтовые сервисы, CDN-шрифты).
6. Менять технологический стек, структуру каталогов, конфигурацию сборки, CI, деплой.
7. Писать тексты, обещающие гарантию оплаты, «безопасную сделку», проверку, которой нет.
8. Убирать метки «ДЕМО», «пилот 18+», «оплата вне платформы».
9. Публиковать, деплоить, пушить в `main`, делать force-push, менять настройки GitHub.
10. Запускать seed, миграции и скрипты изменения данных на базе владельца (`student_marketplace`). Используй изолированные тестовые БД.
11. Выкладывать в коммиты, отчёты, скриншоты `.env`, пароли из `.local/demo-accounts.json`, cookies, строки подключения, личные данные.
12. Перезаписывать эталонные скриншоты, чтобы скрыть регрессию; ослаблять тесты, чтобы они прошли.

## 4. Как соблюдать дизайн-систему

- Все значения — из [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md) и токенов. Нет токена — сначала задача QOSYL-002 или добавление токена с `npm run ui:tokens`.
- Одна primary-кнопка в видимой области. Статусы — через `StatusBadge` (после QOSYL-004). Иконки — только Lucide.
- Без градиентов, стекла, декоративных иллюстраций, бесконечных анимаций. Анимация — только `transform`/`opacity`, токены `motion`, отключение при reduced motion.
- Каждая строка интерфейса — RU и KK; длинные KK-слова проверяй на 320/375 px.
- После изменения визуала обнови [docs/design-system.md](../design-system.md) датированным абзацем, если изменилось правило (не для каждой мелочи).

## 5. Как реализовывать адаптивность

- Mobile-first: базовые стили для телефона, расширения — `@media (min-width: …)` по точкам 600/900/1440 (DESIGN_SYSTEM §3.3). Существующие `max-width`-правила не переписывай массово — только в своём разделе.
- Нет горизонтальной прокрутки страницы на 320–1920 px. Ленты чипов/вкладок — локальная прокрутка с подсказкой края.
- Главное действие на телефоне — в нижней панели (`.detail-actions`) или липкой строке формы.
- Области нажатия ≥ 44 px, поля 16 px.
- Проверяй реальной шириной в браузере, а не только по CSS.

## 6. Как проводить тестирование

Для каждой задачи — «Тестирование» в IMPLEMENTATION_PLAN плюс стандартный набор:

```bash
npm run lint
```

```bash
npm run typecheck
```

```bash
npm test
```

```bash
npx playwright test tests/e2e/<затронутый>.spec.ts
```

```bash
npm run test:ui
```

- При изменении API: `npm run api:generate`, затем `npm run api:check`.
- При изменении токенов: `npm run ui:tokens`.
- При изменении схемы: `npm run test:db` и `npm run test:profile:migration`-подобная проверка на одноразовой БД.
- Не запускай две сборки одновременно (общий `.next`). Тестовый сервер E2E использует production-сборку — после изменений выполняй `npm run build` перед `test:e2e`/`test:ui`, иначе проверяется старый код.
- **Визуальная проверка обязательна:** просмотри скриншоты 375 и 1440 px (светлая и тёмная), а для затронутых форм — клавиатурой (Tab, Shift+Tab, Enter, Esc). Сборка и зелёные тесты ≠ визуальная приёмка.
- Новая логика (чистые функции: `safeNext`, `briefCompleteness`, `profileReadiness`, `pendingActions`, маппинг статусов) — обязательно unit-тесты в `tests/`.
- Изменения публичной проекции — тест, что приватные поля не попали в ответ.

Перед отметкой «готово» пройди по критериям задачи в IMPLEMENTATION_PLAN и FR в [FUNCTIONAL_REQUIREMENTS.md](FUNCTIONAL_REQUIREMENTS.md): каждый критерий — «выполнен, чем подтверждено» или «не выполнен, почему». Сверь раскладку с [UI_UX_SPECIFICATION.md](UI_UX_SPECIFICATION.md). Проверь, что не сломаны соседние сценарии (S1–S7 в FUNCTIONAL_REQUIREMENTS §0), которые касаются изменённых файлов.

## 8. Как отмечать выполненные задачи

В [TASKS.md](TASKS.md) в том же коммите, что и код:

- начало: `[ ]` → `[~]`;
- готово: `[x]` + дата, короткий hash предыдущего коммита задачи или «этот коммит», перечень фактически выполненных проверок;
- заблокировано: `[!]` + причина одной строкой (например, «⚑ В-4 без ответа», «расхождение: поле publishedAt отсутствует в проекции, нужен выбор»).
  Не отмечай `[x]`, если хоть один критерий не выполнен или проверка не запускалась — используй `[~]` и опиши остаток.

## 9. Как вести Git

- Работай в ветке от текущей рабочей ветки владельца (на 15.11.2026 — `feature/opportunities-local`): `git switch -c improvements/<этап>-<кратко>` (например, `improvements/stage1-foundation`). Одна ветка на этап; одна задача — один или несколько логичных коммитов.
- Сообщение коммита: `QOSYL-012: Card shows one set of facts` — ID задачи + что изменилось с точки зрения пользователя, на английском в повелительном/настоящем времени, как в истории репозитория. В теле — зачем, если не очевидно.
- Не смешивай в коммите разные задачи и посторонние правки (форматирование чужих файлов, обновление lock-файла без причины).
- `next dev` переписывает блок в `AGENTS.md` — если в diff появился только он, коммить его вместе с работой (см. AGENTS.md), не удаляй.
- Не пушь в `main`, не делай force-push, не создавай PR, пока владелец не попросит. `git push` своей ветки — только по просьбе владельца.
- Перед коммитом: `git diff --check`, `git status` (нет `.env`, `.local/`, отчётов Playwright, скриншотов в индексе).

## 10. Как отчитываться

После каждой задачи — короткий отчёт (в ответе владельцу; для этапа — файл `docs/qa/qosyl-improvements-<дата>.md` в QOSYL-060):

```
QOSYL-XXX — <название>
Сделано: <2–4 пункта, что изменилось для пользователя>
Файлы: <список>
Проверки: lint ✓, typecheck ✓, unit 512/512 ✓, e2e workflow 21/21 ✓, ui 375/1440 light/dark ✓ (просмотрены)
Не проверено: <что и почему>
Расхождения с документацией: <нет | описание и принятое решение>
Следующая задача: QOSYL-YYY
```

Указывай реальные числа из вывода команд. Не пиши «всё работает», если проверка не запускалась. Красный тест не скрывай: приводи вывод и причину.

**Когда остановиться и спросить владельца:** задача с ⚑ без ответа; документ противоречит коду или существующему правилу из `docs/`; требуется миграция, новая зависимость или изменение контракта, не описанное в задаче; тест падает по причине, не связанной с твоим изменением, и это блокирует проверку; оценка задачи выросла более чем вдвое.
