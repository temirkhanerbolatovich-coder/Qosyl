# Функциональные требования

Каждое требование FR-NNN соответствует задаче QOSYL-NNN. Если требование противоречит существующему поведению, описанному в `docs/` (модерация, согласия, оплата, видимость), — **приоритет у существующего поведения**; остановитесь и опишите конфликт (см. [CODEX_INSTRUCTIONS §3](CODEX_INSTRUCTIONS.md#3-что-запрещено-без-согласования)).

Неизменные правила для всех FR:

- Сервер — источник истины: права, статусы, валидация (`src/lib/validation.ts`) проверяются на сервере; клиентские проверки — только подсказки.
- Публичные данные — только через проекции `src/server/marketplace/projections.ts`; приватные поля (`locationPrivate`, `contactPrivate`, отклики, сдачи, аудит) не попадают в публичные ответы.
- Все тексты — RU и KK; «ДЕМО», «оплата вне платформы, Qosyl не удерживает и не гарантирует оплату», «пилот 18+» сохраняются.
- Ответ API — `{data}` или `{error, code, fields?}` (`src/server/api/http.ts`); новые поля только добавляются, существующие не переименовываются.

## FR-001. Продление демо-заказов (QOSYL-001) — отменено

Решение владельца В-7: не реализовывать. Требований нет. Демо-заказы ведут себя как сейчас: создаются seed'ом один раз и истекают по общим правилам.

## FR-003. Пустой каталог (QOSYL-003)

- **Назначение:** превратить «0 проектов» в понятный следующий шаг.
- **Логика:** после завершения загрузки: если `total=0` и в URL нет параметров фильтра/поиска (кроме `sort`, `page`) → состояние «нет открытых проектов»; если параметры есть → состояние «нет по фильтрам» со списком активных фильтров.
- **Результат:** «нет открытых»: заголовок, объяснение «Новые проекты появляются после проверки модератором» — **без сроков** (решение В-8), кнопки «Стажировки и возможности» (→ `/opportunities`) и «Разместить задачу» (→ `/client/projects/new`); для студента — ссылка «Заполнить профиль». «Нет по фильтрам»: чипы с «×», «Сбросить все».
- **Ошибки:** ошибка загрузки → `LoadState` с «Повторить», а не пустое состояние.
- **Критерии:** пустое состояние не появляется во время загрузки; оба варианта различимы; ссылки работают; в текстах нет обещаний сроков модерации или откликов.

## FR-005. Состояние «не найдено» (QOSYL-005)

- **Логика:** `useData` сохраняет HTTP-статус и `code` ошибки. Для 404/кода «не найден» (уточнить фактический код в `src/server/marketplace/queries/public.ts`) детальная страница показывает состояние «Проект закрыт или ещё не опубликован» + «К каталогу проектов» (+ похожие после QOSYL-014). Для прочих — текущее сообщение и «Повторить».
- **Ошибки:** неизвестный формат ответа → общая ошибка с «Повторить».
- **Критерии:** 404 без «Повторить»; 500/офлайн с «Повторить»; формат ответа API не изменён.

## FR-010/011. Фильтры каталога проектов (QOSYL-010, QOSYL-011)

- **Назначение:** единая модель фильтрации с каталогом возможностей.
- **Сценарий (телефон):** «Фильтры · 2» → нижняя панель → выбор → «Показать 5» → панель закрыта, URL обновлён, список обновлён, фокус на заголовке результатов.
- **Логика:** параметры URL — существующие (`q, category, skill, mode, city, minBudget, maxBudget, difficulty, maxHours, dueBefore, sort, page`); `parseCatalogQuery` (`src/lib/catalog-query.ts`) не менять. Черновой счётчик — запрос `view=catalog` с черновыми параметрами, debounce 300 ms, отмена предыдущего запроса (`AbortController`). Применение сбрасывает `page`. Чип «×» удаляет один параметр (для бюджета — пару). Быстрые пресеты: `maxHours=5`, `dueBefore=<сегодня+3 дня>`, `difficulty=beginner_friendly`, `mode=remote`.
- **Ошибки:** ошибка счётчика → кнопка «Показать результаты» без числа (не блокирует применение); невалидный параметр URL → сервер возвращает ошибку валидации, UI показывает «Фильтр не распознан, сброшен» и удаляет параметр.
- **Критерии:** на 375 px первая карточка ≤ 640 px от верха; Esc закрывает панель и возвращает фокус на кнопку «Фильтры»; «Сбросить» в панели очищает черновик, но не применяет до «Показать».

## FR-012. Карточка проекта (QOSYL-012)

- **Вход:** публичная проекция заказа (+ `publishedAt`).
- **Логика:** относительная дата: < 24 ч — «сегодня», 1 день — «вчера», 2–6 — «N дня/дней назад» (правильные формы RU и KK), ≥ 7 — дата `date()`. Описание — `problem || description`, 2 строки. Срок — `date(dueAt)`. Демо-префикс «ДЕМО:» убирается из заголовка (как сейчас) и показывается бейджем.
- **Критерии:** структура по [DESIGN_SYSTEM §6.3](DESIGN_SYSTEM.md#63-карточка-проекта-projectcard); высоты в пределах цели; приватные поля не появились в JSON (тест).

## FR-013. Возврат к каталогу (QOSYL-013)

- **Логика:** при переходе из каталога в `sessionStorage['qosyl:lastCatalog']` пишется `location.pathname + location.search`, если путь начинается с `/projects` и не содержит `//`. Ссылка «К каталогу проектов» использует это значение, иначе `/projects`.
- **Критерии:** фильтры и страница сохраняются; посторонние значения игнорируются.

## FR-014. Страница проекта (QOSYL-014)

- **Логика действий по роли (существующая, сохраняется):** гость → «Откликнуться» (FR-018); пользователь без роли студента → «Добавить роль исполнителя»; студент → форма отклика/редактирования/отзыва; владелец → «Управление заказом»; назначенный → «К работе». Новое: если `demo && !demoApplicationsAllowed` → вместо кнопки текст «Отклики на этот пример отключены».
- **Похожие:** запрос `view=catalog&category=<категория>`; исключить текущий id; первые 3; при ошибке или 0 — блок скрыт (ошибку не показывать).
- **Мобильная панель (≤ 800 px):** бюджет (numeric) + главное действие роли; панель не перекрывает поля формы отклика (при открытой форме панель скрывается).
- **Критерии:** каждое значение (бюджет, часы, срок, формат, уровень) — 1 раз; панель видна в первом экране на 375 px; похожие не содержат текущий заказ.

## FR-015. Памятка безопасности (QOSYL-015)

- **Содержимое (RU, KK — перевод):** 1) «Оплата проходит напрямую между вами и заказчиком, вне Qosyl. Платформа не удерживает деньги и не гарантирует выплату.» 2) «Не переводите предоплату и не отправляйте документы, пароли и коды.» 3) «Фиксируйте договорённости в условиях заказа — их видят обе стороны.» 4) «Если что-то не так — нажмите «Пожаловаться»; модератор проверит.»
- **Критерии:** нет слов «гарантия оплаты», «безопасная сделка», «защита платежа» в утвердительном смысле (unit-тест строки).

## FR-016. О заказчике (QOSYL-016)

- **Вход (публично):** отображаемое имя/организация (уже в проекции), `verificationStatus`, `memberSince` (месяц/год `User.createdAt`), `completedProjects` (count заказов клиента со статусом `completed` и `demo=false`).
- **Логика:** `completedProjects=0` → «Новый заказчик на Qosyl». Пояснение `verified`: «Модератор проверил организацию и способ связи. Это не гарантия оплаты». Не проверен: «Модератор проверил текст заказа, но не организацию».
- **Ошибки:** агрегат не загрузился → блок показывает только имя и статус проверки.
- **Критерии:** в ответе нет id/названий других заказов; демо не учитывается; тест проекции.

## FR-017. Диапазон откликов (QOSYL-017, В-4: да)

- **Логика:** count откликов со статусом `active` + `selected` → код `none|lt5|5to10|gt10`. Отдаётся только код.
- **Критерии:** точное число не утекает в публичный ответ.

## FR-018. Возврат после входа (QOSYL-018)

- **Назначение:** не терять заказ, ради которого человек регистрируется.
- **Вход:** query `next` на `/auth/login`, `/auth/register`, `/onboarding`.
- **Логика `safeNext(value)`:** принять, если строка, длина ≤ 512, начинается с `/`, второй символ не `/` и не `\`, нет `://`, нет управляющих символов, после `new URL(value, 'http://x')` origin = `http://x`; иначе `/dashboard`. Передача: email-вход/регистрация → `callbackURL = safeNext(next)`; Google → тот же `callbackURL`; если у пользователя нет ролей → `/onboarding?role=student&next=<next>`; onboarding после сохранения → `safeNext(next)`. На странице заказа после возврата с `?apply=1` форма отклика раскрыта и получает фокус.
- **Ошибки:** невалидный `next` молча заменяется `/dashboard`; подтверждение почты (не локальный режим) — письмо ведёт на `callbackURL` с тем же `next`.
- **Критерии:** сценарий S1 проходит без ручной навигации; open-redirect кейсы (`https://evil.com`, `//evil.com`, `/\evil.com`, `javascript:…`, `%2F%2Fevil.com`) → `/dashboard` (unit-тесты).

## FR-020. Форма заказа: «По шагам» и «Все поля» (QOSYL-020, В-9)

- **Назначение:** новичку — пошаговый путь, опытному заказчику и при редактировании — всё на одной странице; оба варианта всегда доступны (решение В-9 «совместить»).
- **Сценарий:** заказчик открывает форму → видит переключатель «Вид формы: По шагам | Все поля» → заполняет в любом режиме, переключаясь при необходимости → «Проверка» → отправка (см. [UI_UX_SPECIFICATION.md](UI_UX_SPECIFICATION.md), §6 «Публикация заказа»).
- **Логика:**
  - Одно состояние формы на оба режима; режим влияет только на отображение.
  - Режим по умолчанию: создание — `steps`, редактирование — `all`; если в `localStorage['qosyl-project-form-mode']` есть `steps|all` — он; ошибки чтения storage игнорируются.
  - Валидация шага при «Далее» и раздела при «Отправить»: те же ограничения, что `projectFields` в `src/lib/validation.ts` (title 8–140, problem 10–1500, deliverables 10–3000, criteria 1–15 по 3–500, budget 1–10 000 000, hours 1–160, город обязателен для onsite/hybrid). Ошибки сервера с `fields` маппятся на поля; в `steps` открывается шаг с первой ошибкой, в `all` — прокрутка и фокус на первое поле с ошибкой.
  - Переключение `steps → all` и обратно не теряет ввод, ошибки и выбранный шаблон.
- **Вход:** поля формы, опциональный шаблон, существующий заказ (для редактирования).
- **Результат:** тот же payload команд `createProject`/`updateProject` в обоих режимах.
- **Ошибки:** сеть → ввод сохраняется, сообщение с «Повторить»; сессия истекла → сообщение и ссылка на вход с `next` (FR-018).
- **Критерии приёмки:**
  - Дано заполненные шаги 1–2 в режиме «По шагам» → переключение на «Все поля» → все значения на месте.
  - Дано ошибка в бюджете при отправке из «Все поля» → переключение на «По шагам» открывает шаг 3.
  - API не менялся (`npm run api:check`); существующие E2E шаблонов проходят; переключение языка не теряет ввод.

## FR-021. Предпросмотр и полнота (QOSYL-021)

- **Логика `briefCompleteness(form)`** → список `{id, done, hint}`: `problem` (≥ 10 симв.), `deliverables` (≥ 10), `criteria` (≥ 2 строк), `skills` (≥ 1), `budget` (> 0), `due` (≥ сегодня + 2 дня), `hours` (≤ 40 — подсказка «микрозадача»; > 40 — нейтральное предупреждение, не ошибка).
- **Критерии:** чистая функция с unit-тестами; предпросмотр использует тот же `ProjectCard`.

## FR-022. Отправка на модерацию из формы (QOSYL-022)

- **Логика:** «Отправить на модерацию» = сохранить (`createProject` или `updateProject`) → `submitForModeration(projectId)`. Если второй вызов упал: черновик сохранён, сообщение «Черновик сохранён, но отправить не удалось: <причина>» и кнопка «Отправить ещё раз».
- **Критерии:** существующие правила (повторная модерация после правки опубликованного заказа) не меняются.

## FR-023. Число откликов у заказчика (QOSYL-023)

- **Вход:** `_count.applications` из `view=dashboard` с фильтром `status: active` (уточнение владельца от 15.11.2026).
- **Общая выборка:** тот же счётчик активных откликов возвращается для `view=portfolio` и назначенного исполнителя; формат ответа не меняется.
- **Критерии:** число совпадает с данными; 0 → «Откликов пока нет».

## FR-024. «Требует действия» (QOSYL-024)

- **Логика:** чистая функция `pendingActions(account, viewer)` → список `{projectId, kind, title, href}` по правилам из IMPLEMENTATION_PLAN QOSYL-024; сортировка: ближайший `dueAt` первым.
- **Критерии:** unit-тесты на каждый `kind`; демо-заказы помечены бейджем.

## FR-025. Подсказки сроков (QOSYL-025)

- **Логика:** формулировки строятся из `dueAt`/`expiresAt` заказа и фактического поведения `src/server/lifecycle/` (проверить, что происходит с откликами при истечении заказа, и написать ровно это). Сроки работы платформы и ожидаемое время ответа не обещать (решение В-8) — только даты конкретного заказа.

## FR-026. Кандидат на странице откликов (QOSYL-026)

- **Вход (только владельцу заказа):** для каждого отклика — `student.name`, аватар (через существующий `/api/avatars/{id}` с его правилами), `headline`, `institution`/`studyYear` (если не в `hiddenFields`), `skills`, `isPublic`, `confirmedWorks` (count PortfolioRecord с публикацией).
- **Логика:** ссылка «Открыть профиль» только при `isPublic=true`.
- **Ошибки:** нет прав → существующий 403.
- **Критерии:** интеграционный тест: владелец видит, чужой заказчик — 403, скрытые поля не приходят.

## FR-030. Готовность профиля (QOSYL-030)

- **Логика `profileReadiness(profile)`:** 9 пунктов (аватар; headline; discipline или institution; bio ≥ 80; skills ≥ 3; weeklyHours > 0; ≥ 1 публичный кейс или подтверждённая работа; ≥ 1 ссылка; isPublic). Возвращает `{done, total, items[{id, done, anchor}]}`.
- **Критерии:** unit-тесты; виджет скрывается при 9/9 (заменяется «Профиль готов»).

## FR-032. Мои отклики (QOSYL-032)

- **Логика:** активные — `active`, `selected` при незавершённом заказе; архив — остальные. Шкала: `active` → шаг 2 «Выбор заказчика»; `selected` → «Вы выбраны» (success); `not_selected` → «Не выбран»; `withdrawn` → «Отозван».

## FR-033. Подходит вам (QOSYL-033)

- **Логика:** `view=catalog&sort=relevance` (сервер учитывает навыки профиля); показать 3; подпись совпавших навыков — пересечение `profile.skills` и `project.skills` без учёта регистра.

## FR-035. Карточка возможности (QOSYL-035)

- **Логика:** не менять тексты честности («Уточняйте у организатора»), только объединить неизвестные условия в одну строку и убрать дубль формата.

## FR-036. Главная: блок проектов (QOSYL-036, В-1)

- **Логика:** порядок главной не меняется (возможности первыми). В блоке «Проекты от заказчиков» — до 3 карточек `view=catalog&sort=newest`; при 0 или ошибке карточки не рендерятся, текст блока и кнопки «Найти проект» / «Разместить задачу» остаются.
- **Критерии:** `tests/e2e/home-discovery.spec.ts` проходит без изменения ожиданий порядка.

## FR-007. Шапка и навигация по роли (QOSYL-007)

- **Логика:** «Избранное» — если `viewer.roles` содержит `student`. Главное действие шапки: гость — «Начать»; `client` — «Разместить заказ»; только `student` — нет кнопки.

## FR-009. Очистка тестовых БД (QOSYL-009)

- **Логика:** удаляются только имена, соответствующие `^student_marketplace_e2e_ui_[a-f0-9]{12}$`; подключение только к loopback (как `scripts/test-db.mjs`); без `--yes` — dry-run.

- **Критерии:** интеграционные тесты повторов, отключения, прав.

## FR-042. Отметка просмотра отклика (QOSYL-042, В-10: да)

- **Логика:** при открытии страницы откликов владельцем — команда `markApplicationsViewed(projectId)`: для откликов этого заказа с `viewedAt IS NULL` ставится `now()`, событие аудита. Повторный вызов ничего не меняет.

## FR-043. Категория «Фото и видео» (QOSYL-043, В-3)

- **Логика:** в массив `categories` добавляется `photo_video` («Фото и видео» / «Фото және бейне», иконка `Camera`); подпись `writing` меняется на «Тексты и переводы» / «Мәтіндер мен аударма» без изменения кода значения; «Репетиторство» и «Мероприятия» не добавляются. Фильтр каталога принимает новое значение автоматически (`parseCatalogQuery` импортирует тот же массив — `src/lib/catalog-query.ts:36`).
- **Критерии:** заказы с прежними категориями отображаются как раньше; `?category=photo_video` фильтрует; неизвестная категория по-прежнему отклоняется.

## FR-046. Dev-вход по 127.0.0.1 (QOSYL-046)

- **Логика:** только при `LOCAL_DEV_MODE=true`; production-поведение неизменно.
