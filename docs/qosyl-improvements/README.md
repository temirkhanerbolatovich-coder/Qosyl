# Qosyl Improvements — точка входа для исполнителя

Дата подготовки: 15.11.2026. Ветка на момент подготовки: `feature/opportunities-local` (HEAD `d82dbbe`).

## Что такое Qosyl

Qosyl — платформа для студентов, молодых специалистов и бизнеса в Казахстане. Две линии продукта:

1. **Каталог возможностей — главное направление (решение владельца В-1, 15.11.2026).** Стажировки, гранты, стипендии, конкурсы, мероприятия из внешних источников с редакторской проверкой, избранным, напоминаниями, сравнением и подписками; гид по поступлению; PDF-резюме. Главная и навигация остаются «возможности первыми».
2. **Биржа микропроектов.** Бизнес публикует небольшую задачу с результатом, критериями приёмки, бюджетом и сроком → модерация → студенты бесплатно откликаются → заказчик выбирает исполнителя → стороны подтверждают условия → сдача, правки, приёмка → двустороннее закрытие → работа попадает в портфолио студента с согласия обеих сторон. Оплата — напрямую между участниками, вне платформы; Qosyl не удерживает деньги и не гарантирует выплату.

Стек: Next.js 16.4 (App Router) + React 19.3 + TypeScript, PostgreSQL + Prisma 7.10, Better Auth, Zod, Lucide, собственная CSS-система на токенах (в коде сейчас Indigo «Qosyl Modern»; утверждённая палитра — Deep Blue/Teal, возврат — задача QOSYL-006), RU/KK, светлая/тёмная тема, Vitest + Playwright + axe. Подробно — [PRODUCT_AUDIT.md §2](PRODUCT_AUDIT.md#2-текущее-состояние-продукта).

## Цели обновления

1. **Починить основной сценарий биржи** (P0): возврат к заказу после регистрации, число откликов и профиль кандидата у заказчика, понятное пустое состояние каталога.
2. **Сделать каталог и страницу задачи удобными на телефоне** и единообразными с каталогом возможностей.
3. **Упростить публикацию задачи для бизнеса:** мастер, предпросмотр, полнота ТЗ, понятный путь к модерации.
4. **Сделать доверие видимым и честным:** проверка заказчика с пояснением, памятка безопасности, подтверждённые работы первыми в профиле.
5. **Кабинеты про действия, а не про счётчики.**
6. **Вернуть утверждённую палитру Deep Blue/Teal и укрепить визуальную систему** (типографика, поверхности, статусы, брейкпоинты) без смены стека.
7. **Сохранить возможности главным разделом**, усилив на главной вход в биржу (свежие задачи, «Разместить задачу»).

Не цели: переписывание проекта, смена стека, платежи/escrow, чат, AI, новые внешние сервисы.

## Общие правила реализации (кратко)

1. Улучшаем существующий продукт: минимальные изменения, переиспользование компонентов, без смены архитектуры и стека.
2. Бизнес-правила, роли, модерация, согласия, видимость, ограничения оплаты, метки ДЕМО — неизменны.
3. Публичные данные — только через проекции; новые поля API — только добавлением, с OpenAPI.
4. Без новых зависимостей и внешних сервисов без согласования.
5. RU и KK одновременно; светлая и тёмная тема; 320–1920 px без горизонтальной прокрутки.
6. Каждая задача: код + тесты + визуальная проверка + отметка в TASKS.md + честный отчёт.
7. Решения владельца — в разделе «Решения» ниже; они обязательны и имеют приоритет над рекомендациями в остальных документах.

## Риски

1. **Пустой каталог проектов важнее любого дизайна.** Без реальных заказчиков (на production 04.11 — 0 опубликованных заказов) улучшения биржи не дадут эффекта. Демо-заказы по решению В-7 не продлеваются, поэтому локальное демо тоже будет показывать пустой каталог после истечения примеров — проверяйте UI биржи на изолированной тестовой БД (там seed создаёт свежие заказы). Нужен операционный план привлечения заказчиков — вне рамок кода.
2. **Редакторская очередь возможностей** (217 материалов ожидают проверки локально) — каталог выглядит беднее, чем мог бы.
3. **Ожидание «гарантии оплаты»** (78% опроса) конфликтует с моделью «оплата вне платформы». Тексты должны оставаться честными; риск разочарования снижается видимостью доверия, а не обещаниями.
4. **Конфликты файлов** — `catalog.tsx`, `project-detail.tsx`, `dashboard.tsx`, `design-system.css` затрагиваются многими задачами; выполнять последовательно (см. IMPLEMENTATION_PLAN «Последовательность»).
5. **Регрессии локализации** — каждая новая строка нужна в RU и KK; KK-тексты требуют редактуры носителем языка (открытый пункт F06).
6. **Устаревшая сборка в тестах** — E2E/UI используют production-сборку; без `npm run build` тесты проверяют старый код.
7. **Миграции (040, 042)** — только после backup и проверки на отдельной БД.
8. **Смена палитры (006)** затрагивает все экраны: обязательны проверка контраста `npm run ui:tokens` и просмотр скриншотов обеих тем до и после.
