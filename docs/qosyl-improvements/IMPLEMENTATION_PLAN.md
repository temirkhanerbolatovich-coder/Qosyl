# План реализации

Каждая задача — небольшой независимый пакет: одна ветка или один коммит, свои тесты, своя запись в [TASKS.md](TASKS.md). Требования к поведению — в [FUNCTIONAL_REQUIREMENTS.md](FUNCTIONAL_REQUIREMENTS.md), раскладка экранов — в [UI_UX_SPECIFICATION.md](UI_UX_SPECIFICATION.md), визуальные правила — в [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md), порядок работы — в [CODEX_INSTRUCTIONS.md](CODEX_INSTRUCTIONS.md).

**Как связаны документы:** здесь задачи сгруппированы **тематически** (блоки A–G). **Порядок выполнения** — этапы 1–7 в [TASKS.md](TASKS.md) и раздел «Последовательность» в конце этого файла. Номер блока не означает очередь.

**Сложность:** S — до полудня, ≤ 3 файлов, без изменений API; M — 1–2 дня, несколько компонентов или обратно совместимое расширение API; L — 3+ дней или миграция БД.

**Стандартная проверка** (ниже — «станд. проверка»): `npm run lint`, `npm run typecheck`, `npm test`, затронутые E2E (`npx playwright test tests/e2e/<файл>`), `npm run test:ui` (строгий режим: 0 serious/critical axe, 0 переполнений), просмотр скриншотов 375 и 1440 px в светлой и тёмной теме, RU и KK. При изменении API — `npm run api:generate` и `npm run api:check`. При изменении токенов — `npm run ui:tokens`.

**Метки решений.** «⚑ В-N» — задача ждёт решения владельца из списка вопросов в [README.md](README.md#вопросы-требующие-решения-владельца). Без ответа такую задачу не начинать; если ответ записан в README, следовать ему.

### QOSYL-001 — Демо-заказы не устаревают

- **Приоритет:** P0. **Сложность:** S.
- **Описание:** `prisma/seed.ts` создаёт 8 демо-заказов через `upsert` с `update: {}`; через 14 дней они истекают и каталог становится пустым. Сделать ветку `update`, которая для **демо-заказов без назначенного исполнителя и в статусе `published`/`expired`** продлевает `dueAt`/`expiresAt` на +14 дней от запуска seed и возвращает статус `published`. Реальные заказы, назначенные демо-заказы и любые другие поля не трогать.
- **Файлы:** `prisma/seed.ts`; документация `docs/local-demo.md` (абзац «Демо-заказы продлеваются при каждом `npm run db:seed`/`npm run demo`»).
- **Зависимости:** нет. ⚑ В-7 (рекомендация: делать).
- **Критерии завершения:** после `npm run db:seed` на БД с истёкшими демо-заказами каталог показывает 8 заказов; заказ с `assignedStudentId` или статусом кроме `published`/`expired` не меняется; `demo=false` не меняется никогда; повторный seed идемпотентен.
- **Тестирование:** интеграционный тест на изолированной БД (по образцу `tests/*.integration.mts`): создать истёкший демо-заказ, назначенный демо-заказ и реальный заказ → seed → проверить поля. Станд. проверка. **Не запускать seed на БД владельца без его разрешения.**

### QOSYL-046 — Вход в dev-режиме по 127.0.0.1

- **Приоритет:** P2. **Сложность:** S.
- **Описание:** `npm run dev` слушает `127.0.0.1`, а проверка origin (`requireSameOrigin`, `trustedOrigins` в `src/lib/auth.ts`) принимает только `config.baseUrl`. При открытии `http://127.0.0.1:3000` вход отклоняется «Запрос разрешён только с сайта платформы». Решение без ослабления production: в `LOCAL_DEV_MODE` добавлять в доверенные origin пару `localhost`/`127.0.0.1` того же порта **или** документировать, что открывать нужно `config.baseUrl`, и выводить этот URL в консоль `npm run dev`. Выбрать минимальный вариант, согласовать с `.agents/skills/qosyl-security`.
- **Файлы:** `src/lib/auth.ts`, `src/server/api/http.ts`, `src/lib/config.ts`, `docs/development-guide.md`.
- **Зависимости:** нет.
- **Критерии:** production-конфигурация не меняется (тест: при `LOCAL_DEV_MODE=false` чужой origin отклоняется); локальный вход работает по обоим адресам или документирован.
- **Тестирование:** `tests/api-http.test.ts` + новый кейс.
