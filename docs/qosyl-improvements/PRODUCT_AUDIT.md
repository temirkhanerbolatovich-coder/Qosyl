## 2. Текущее состояние продукта

### 2.1 Стек и архитектура (сохранять)

- **Next.js 16.4 App Router + React 19.3**, TypeScript 5.9, Tailwind 4 (через PostCSS) + собственные CSS-файлы `src/app/globals.css` (2724 строки) и `src/app/design-system.css` (1707 строк), токены — `src/lib/design-tokens.json` → `src/app/design-tokens.css`.
- **PostgreSQL + Prisma 7.10** (`@prisma/adapter-pg`), Better Auth 1.7 (email/пароль, Google), Zod 4, Lucide, sharp, pdf-lib.
- Серверная логика отделена от HTTP: `src/app/api/*` → `src/server/marketplace/index.ts` (30 команд, 10 видов чтения) → `commands/`, `queries/`, `projections.ts` (явные публичные `select`). Команды в Serializable-транзакциях с повторной проверкой ролей и аудитом. Это сильная сторона — **не переписывать**.
- Клиентская загрузка данных: собственный хук `useData(view, params)` и `useAction()` в `src/components/platform.tsx`; RU/KK через `useI18n()`/`useMarketplaceCopy()`.
- Тесты: Vitest (unit/интеграция), Playwright E2E (`tests/e2e`, 30 спецификаций), UI-качество (`tests/ui-quality`, 18 спецификаций, 7 ширин × 2 темы, axe + overflow), GitHub CI.
- Фоновые процессы: worker жизненного цикла, сбора контента, уведомлений сохранённых поисков.

### 2.2 Две продуктовые линии

1. **Биржа микропроектов** (`/projects`, `/client/*`, `/student/*`, `/work/[id]`, `/talent/[id]`): публикация → модерация → бесплатный отклик → выбор исполнителя → согласование версии условий обеими сторонами → сдача → правки → приёмка → двустороннее закрытие → заявления об оплате (вне платформы) → отзывы → портфолио с согласием обеих сторон. Закрытые файлы, 8 шаблонов задач, споры, жалобы.
2. **Каталог возможностей** (`/opportunities`, `/admissions`): стажировки, гранты, стипендии, конкурсы, мероприятия из внешних источников; редакторская модерация, избранное, заметки, напоминания о дедлайнах, сравнение, сохранённые поиски с уведомлениями, гид по поступлению, PDF-резюме.

Главная страница и навигация **сейчас ставят возможности первыми**: шапка «Возможности → Поступление → Проекты»; на главной блок проектов начинается на 1788 px из 2273 (1440 px), карточек проектов на главной нет. Концепция владельца называет основным направлением микропроекты — это расхождение вынесено в вопрос В-1 ([README](README.md#вопросы-требующие-решения-владельца)).

### 2.3 Состояние данных (локально, 15.11.2026)

- `Project`: 8 записей, все `demo=true`, `status=published`, `dueAt=07.11.2026` — **срок истёк, публичный каталог пуст** («0 проектов по вашим условиям»). Причина: `prisma/seed.ts` делает `upsert` с `update: {}`, поэтому демо-заказы создаются с `dueAt = now + 14 дней` один раз и затем не продлеваются.
- `ContentItem`: 6 опубликовано, 217 ожидают редакторской проверки, 4 в архиве.
- В локальном кластере PostgreSQL **210 баз данных**: изолированные UI-прогоны создают `student_marketplace_e2e_ui_<hash>` и не удаляют их. После некорректного завершения восстановление кластера заняло ~4 минуты из-за fsync всех баз.
- По [аудиту 04.11.2026](../qa/full-audit-2026-11-04.md) на production было 0 опубликованных заказов.

## 3. Сильные стороны

1. **Честная и защищённая доменная модель.** Неизменяемая история условий/сдач, двусторонние подтверждения, скрытие контактов до согласования, явное «оплата вне платформы», метки ДЕМО. Это редкость для студенческих проектов и прямое преимущество перед классифайдами по доверию.
2. **Структура ТЗ заложена в модель заказа:** проблема, описание, результат, критерии приёмки (1–15), навыки, уровень, часы, бюджет, срок. У большинства бирж это свободный текст.
3. **Качество инженерной базы:** проекции публичных полей, OpenAPI, CI, изолированные тестовые БД, проверка контраста токенов, axe-проверки 7 ширин × 2 темы.
4. **Локализация RU/KK** с сохранением ввода при переключении.
5. **Возможности уже доведены до хорошего уровня UX** на этапах 0–2 (14.11.2026): боковые фильтры, нижняя панель «Показать N», «Следить за поиском», тосты с «Отменить», токены движения, страница возможности с похожими.
6. **Шаблоны задач** по специальностям снижают порог для бизнеса.
7. **Портфолио двух уровней:** «Подтверждено заказчиком» (PortfolioRecord) и самостоятельные кейсы.

## 6. Архитектурные наблюдения

1. **Нет серьёзной архитектурной проблемы, требующей переписывания.** Границы API/сервер/проекции правильные.
2. **Публичные поля заказа — только через `src/server/marketplace/projections.ts`.** Любое новое поле в карточке (число откликов, дата публикации, статистика заказчика) добавляется туда же, с обновлением OpenAPI (`npm run api:generate` / `api:check`) и проверкой, что не раскрываются приватные данные (`locationPrivate`, `contactPrivate`, отклики).
3. **Сортировка по релевантности читает id/заголовок/навыки всего набора в память** ([architecture.md](../architecture.md)). При росте каталога (>2–3 тыс. опубликованных) перенести в SQL. Сейчас не трогать.
4. **CSS-долг** (два слоя, разрозненные брейкпоинты) — постепенное сведение к токенам (QOSYL-002, QOSYL-044) без переписывания компонентов.
5. **Seed не идемпотентен по времени** — демо-контент «протухает» (QOSYL-001).

## 7. Потенциал развития

- **Доверие как продукт.** Опрос: 78% хотят гарантию оплаты, 49% — проверенного заказчика. Гарантию дать нельзя, но можно сделать видимыми проверку заказчика, историю завершённых заказов, отзывы, подтверждённое портфолио, критерии приёмки и памятку безопасности. Это отличает Qosyl от OLX/Telegram-чатов.
- **«Первый заказ за выходные».** 44% хотят задачи на 1–3 дня, 58% — до 5 часов в неделю. Быстрые фильтры, метка «Можно без опыта» и шаблоны уже есть; не хватает живого потока заказов и возврата к заказу после регистрации.
- **Портфолио как результат.** Подтверждённая работа — главный артефакт для студента; показать её первой в профиле и в отклике.
- **Связка двух линий.** Возможности приводят студентов регулярно; проекты нужны реже, но ценнее. Перекрёстные блоки («Задачи по вашему направлению» в возможностях, «Стажировки по этим навыкам» в проектах) — после стабилизации основного потока (P2).
